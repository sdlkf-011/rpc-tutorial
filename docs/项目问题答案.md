# 项目问题答案

本文对应 [项目问题](项目问题.md) 中的 29 个问题，结合当前 CookRPC 实现说明设计原理与边界。运行步骤、依赖与配置见 [README](../README.md)。扩展建议与已实现能力分开说明，性能结论需要具体测试环境与数据支持。

## 1. 日志模块（spdlog）

### 1.1 为什么选择 spdlog？异步日志如何实现？

项目通过 [log_manager.h](../utils/log_manager.h) 封装 spdlog，统一格式化、日志级别、控制台输出和文件输出。它与项目已使用的 fmt 配合方便，调用点通过 `LOG_INFO` 等宏记录消息。仓库没有与 glog 或 log4cpp 的对比测试，因此选型理由是接口和集成便利，不能据此认定其性能优于其他库。

当前创建的是普通 `spdlog::logger`，日志在调用线程同步写入。异步方案需要改为异步 logger，将记录放入有限队列，由后台线程写入 sink；队列满时必须选择阻塞或丢弃策略，退出时还要协调刷新和后台线程生命周期。这些机制由 spdlog 提供，但项目尚未启用。[spdlog 异步日志说明](https://github.com/gabime/spdlog/wiki/Asynchronous-logging)

### 1.2 多线程日志如何避免竞争？如何滚动？

控制台和文件分别使用 `stdout_color_sink_mt`、`daily_file_sink_mt`，由 sink 内部同步并发写入。`Logger::GetInstance()` 使用函数内静态对象；这保证单例构造安全，但不代表可以并发调用 `Init()` 重配 logger。入口应在启动工作线程之前完成初始化。

示例日志写入 `../logs/cookrpc_YYYY-MM-DD.log`，以进程工作目录解析路径，使用日期文件名计算器在每天零点滚动。格式包含时间、级别和线程 ID，便于关联并发调用。当前没有按文件大小滚动、保留天数限制或集中日志采集配置。

### 1.3 如何调整级别、控制开销？各级别如何使用？

初始化将运行时级别设为 `trace`，但宏是否生成代码还受 `SPDLOG_ACTIVE_LEVEL` 控制。项目未显式定义该编译选项，依赖默认配置下 TRACE/DEBUG 可能已被编译掉，单独修改运行时级别无法恢复这些日志。[spdlog FAQ](https://github.com/gabime/spdlog/wiki/FAQ)

| 级别 | 适合记录的内容 |
| --- | --- |
| TRACE / DEBUG | 帧解析、事件状态、选址等细节，排障时按需开启 |
| INFO | 启动、配置提交、注册成功和退出等生命周期事件 |
| WARN | 可恢复失败、策略回退或临时连接异常 |
| ERROR | 请求失败、协议错误、配置或注册失败 |
| FATAL | 严重错误；项目宏映射到 `critical`，不会自动终止进程 |

当前没有动态修改级别的配置接口。后续可提供受同步保护的级别调整入口，结合限频、采样和异步队列降低开销。同步日志仍可能增加事件线程延迟，应通过压测量化，避免在热路径逐字节打印数据或记录敏感载荷。

## 2. 负载均衡模块

### 2.1 实现了哪些算法？如何感知负载？

[LoadBalancer](../rpc_src/conn_balancer/load_balancer.cc) 支持三种策略：

| 策略 | 当前实现 | 并发保护 |
| --- | --- | --- |
| `random` | 在本次实例列表中随机选择 | 独立互斥锁保护 `std::mt19937` |
| `round` | 用递增索引轮询 | 原子计数器 |
| `weight` | 所有实例视为权重 1，按等权轮询选择 | 原子计数器 |

没有一致性哈希或非等权权重配置，也没有 CPU、队列长度、响应延迟等负载指标采集。若后续加入动态权重，需要明确指标来源、采样周期、异常节点处理及权重快照的一致性。

全局策略对象由 `shared_ptr` 管理，`instance_` 的读写和懒初始化都在同一把锁内完成。选址先取得局部句柄，解锁后执行 `Select()`。句柄保护对象生命周期，策略自己的锁或原子变量保护内部状态；两者解决的问题不同。

### 2.2 如何避免雪崩？如何配合 ZooKeeper 发现服务？

[ZkConnHandler](../rpc_src/conn_balancer/zk_conn_handler.cc) 每次查询指定命名空间下的子节点及地址数据，然后直接对本次局部列表选址。没有全局 `servers_` 中转或发现缓存，不同命名空间的查询结果不会相互覆盖。

每个 `RpcClient` 拥有独立发现处理器，可连接不同 ZooKeeper 集群。处理器通过拥有句柄和 watcher 上下文的会话对象管理连接，查询持有会话快照。切换端点按“解析、校验、连接候选会话、提交”执行：新连接成功后替换配置与句柄，失败保留旧会话。旧回调仅更新旧会话状态，旧句柄在最后一个查询释放后关闭。

客户端建连最多尝试 `retry_times + 1` 次，失败之间固定等待 100 毫秒。客户端会话按实例地址维护熔断器，连续远端建连、收发或协议失败达到阈值后避开该地址，冷却结束允许一次探测；成功关闭熔断，失败重新冷却。有效业务错误和限流响应不计故障。服务端有令牌桶限流、任务队列和响应队列容量限制。当前没有指数退避、抖动或自动业务重试，已经发送的请求需要由调用方根据幂等性决定是否重试。

## 3. 压缩模块

### 3.1 为什么选择 Zstd？如何权衡压缩率与速度？

[ZstdCompress](../rpc_src/compress_data/zstd_compress.cc) 封装 Zstd，提供字符串与二进制接口，支持 1、3、7、19、22 等压缩级别，默认级别为 3。压缩前用 `ZSTD_compressBound()` 分配输出空间，完成后缩减到实际大小。

选型以组件集成和可调压缩级别为出发点。仓库没有 zlib、Snappy、Zstd 在相同数据集上的对比结果。应使用真实 RPC 数据，分别测量压缩率、压缩和解压耗时、内存峰值与端到端延迟，再选择级别，不能只看压缩后字节数。

### 3.2 何时启用压缩？失败如何处理？

RPC 链路通过 TransportCodec 接入 Zstd。两端配置 `transport.compression`，逻辑 body 达到 `compression_threshold` 时尝试压缩，仅在输出更小时设置实际压缩标志。启用传输变换使用 CRP1 格式，接收端按标志解码；配置模式必须一致，没有自动算法协商或静默降级。

当前接口以 `bool` 表示成功或失败。空输入会清空输出并成功返回；压缩失败不保证清空输出，调用者只能在返回 `true` 时消费结果。解压要求帧声明原始大小，并在分配前检查上限，默认最多输出 1 MiB，调用方可显式指定其他上限。未知或无效大小、超限和分配异常均使解压返回 `false` 并清空输出。

网络链路将逻辑 body、wire body 和解压输出分别限制为 1 MiB。压缩编码失败时不发送请求；响应编码超限转换为短错误响应。未获得压缩收益时发送未压缩 body，实际压缩标志保持关闭。

### 3.3 压缩和加密的顺序是什么？

主链路按配置执行以下顺序，未启用的变换直接跳过：

```text
发送：业务序列化 → 压缩 → 加密与认证 → 发送
接收：验证并解密 → 有限大小解压 → 业务反序列化
```

加密后的数据通常不再适合压缩。算法、长度等元数据应纳入认证范围；认证失败时不要解压或交给业务解析。在允许攻击者控制部分明文的场景中，还需评估压缩后长度泄露，不能默认所有载荷都适合压缩。

## 4. 加解密模块

### 4.1 使用 AES 还是 RSA？

[AesEncrypt](../rpc_src/encrypt/aes_encrypt.cc) 使用 OpenSSL EVP 的 AES-256-GCM，通过对称加密同时提供机密性与完整性认证。每次加密生成 12 字节随机 nonce，并附带 16 字节认证 tag。组件由 TransportCodec 接入 RPC 通信，没有 RSA、证书认证或密钥协商实现。

其输出为以下二进制结构的 Base64 编码：

```text
版本（1 字节，当前为 1） | nonce（12 字节） | 密文 | tag（16 字节）
```

版本字节作为附加认证数据参与 GCM 认证。RPC 链路额外认证外层头部、压缩与加密标志、请求/响应方向，拒绝元数据篡改及请求/响应反射。认证通过后才解压和分发。

### 4.2 如何管理密钥、防重放和测试性能？

RPC 加密从 `COOKRPC_MASTER_KEY_HEX` 读取 64 个十六进制字符，转换为 32 字节共享密钥，两端必须使用相同值。缺失或格式错误时配置加载失败，不使用随机密钥或退回明文。每个传输编码器持有不可变密钥实例，配置校验失败保留当前会话。独立 AES 单例仍提供仅在当前进程有效的随机缺省密钥。析构时清理密钥内存；没有密钥轮换、密钥管理服务或跨进程协商机制。

GCM 认证不等于完整防重放。加密连接校验非零且递增的请求序列号，并允许正常计数回绕，拒绝同一连接上的重复或倒退请求。没有跨连接的持久去重、连接挑战或重放窗口，消息加密不能替代 TLS 会话安全。

[AES 测试](../rpc_src/test/aes_encrypt_test.cc) 覆盖往返、非法密文、篡改和随机 nonce 等行为，没有专门的性能基准。性能测试应覆盖不同载荷长度，分别测量加解密吞吐量、延迟以及 Base64 带来的体积和 CPU 开销。

### 4.3 如何处理损坏或解密失败？

解密先检查 Base64、版本、最小长度和密钥状态，再通过 GCM final 验证 tag。只有认证通过才返回成功；失败会清空明文输出，调用者不得继续使用数据。

RPC 认证失败时关闭连接，客户端报告解码或认证失败，错误数据不会进入业务处理。模式不匹配同样拒绝通信。日志只记录必要的错误类型，不记录密钥、明文或完整密文；加密未启用时的结构检查不提供密码学认证。

## 5. 序列化与反序列化

### 5.1 为什么同时提供 JSON 和 Protobuf？如何跨语言？

[SerializerManager](../rpc_src/serializer/serializer_manager.h) 对普通类型使用 nlohmann-json，对继承 `google::protobuf::MessageLite` 的生成类型使用 Protobuf。普通类型通过 `to_json` / `from_json` 定义映射；Protobuf 使用 `SerializeToString()` / `ParseFromString()`。类型与指定格式不匹配时返回失败。

JSON 便于查看和调试，示例 `RpcService.Echo` 使用 JSON。Protobuf 适合依据 schema 生成多语言类型。项目的 [message.proto](../protos/message.proto) 提供 `rpc.tutorial` 消息，但实际外层 RPC 请求和响应由自定义二进制协议编码，没有使用这些生成消息替代外层帧。

跨语言客户端必须同时实现外层帧格式，并与服务端约定业务载荷的编码。仅生成 Protobuf 类不足以直接调用示例 JSON Echo；当前协议没有携带序列化类型或协商信息。

### 5.2 如何处理字段兼容？如何优化自定义序列化？

对未来使用的 Protobuf 业务消息，应保留已有字段编号，新增字段使用新编号，删除字段后预留其编号和名称，并避免不兼容的类型变化。这些规则适用于 Protobuf 消息，不会自动赋予当前自定义 RPC 帧版本兼容能力。[Proto3 字段更新规则](https://protobuf.dev/programming-guides/proto3/)

JSON 和 Protobuf 适配器先解析到临时对象，再在解析成功后更新目标，减少解析错误造成的半更新状态。涉及内存分配或用户类型赋值异常时，仍需按具体类型评估异常保证。

外层协议预先计算长度、检查上限并预留输出空间，减少重复扩容。进一步优化应先定位字符串复制、分配和编码热点；可以评估缓冲区复用，但不能让异步发送引用已经销毁或被修改的业务缓冲区。

## 6. ZooKeeper 节点注册

### 6.1 为什么选择 ZooKeeper？持久与临时节点有什么区别？

项目使用 ZooKeeper C client 演示会话、节点和 watch 驱动的服务注册。没有 etcd 后端或两者的性能与运维对比，选型结论限于当前教学实现。替换后端时，需要重新映射会话所有权、租约过期、监听和恢复机制。

[ServiceRegistry](../rpc_src/registry/service_registry.cc) 使用持久节点保存 `/cookrpc` 根目录与服务目录，实例使用临时节点：

```text
/cookrpc                                      持久根目录
/cookrpc/cookrpc_service                      持久服务目录
/cookrpc/cookrpc_service/127.0.0.1:8989       临时实例，数据为地址
```

持久节点不会因创建会话结束而自动删除；临时节点属于创建它的会话，在该会话结束后删除。临时节点反映会话存活，不能代替业务健康检查。

### 6.2 如何注册、发现和恢复过期会话？

注册成功需要取得实例所有权，不能只根据 `ZNODEEXISTS` 判断：

| 已存在节点 | 处理方式 |
| --- | --- |
| 持久父路径 | 检查 `ephemeralOwner == 0` 后复用 |
| 当前会话的实例，地址数据匹配 | 作为重复注册成功 |
| 当前会话的实例，地址不匹配 | 返回冲突 |
| 其他会话的实例 | 设置 watch，有限等待删除后重试创建 |
| 实例路径被持久节点占用 | 返回冲突 |

所有权通过 `Stat.ephemeralOwner` 与 `zoo_client_id()` 比较。存在检查与数据读取均校验状态；节点在检查、设置 watch、读取和创建之间消失或再次出现时，重新进入检查与创建流程。watch 是一次性通知，创建、存在检查和数据读取使用 ZooKeeper 异步 API；调用方只等待总期限内的结果，默认 3 秒，期限也覆盖注册操作排队和 watch 等待。

completion 上下文由 SDK 持有的共享对象管理，超时后迟到回调只发布结果，不访问注册器或提交注册。结果不确定时退役整个会话，由恢复线程在锁外关闭旧会话后重放已确认注册；超时创建的临时节点随旧会话关闭或过期清理。

watcher 只发布会话状态并唤醒恢复线程。恢复线程在会话终止后建立新会话，重放已成功注册的服务；不会在回调里同步重连或注册。每个会话拥有独立上下文，退出时先停止并等待恢复线程，再关闭句柄，关闭时不持有 watcher 使用的状态锁。

发现通过客户端自己的会话读取服务目录和实例数据；注册与发现使用各自的连接。发现会话过期后，在后续查询中重建连接。目前没有常驻实例列表缓存或持续的子节点 watch。

## 7. RPC 协议定义

### 7.1 协议头如何设计？如何解决粘包拆包？

[RpcHeader](../rpc_src/protocol/rpc_protocol.h) 固定为 12 字节，整数采用网络字节序：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 字节 | magic，`0x43525043`，对应 `CRPC` |
| 4 | 4 字节 | body 长度，不包含头部 |
| 8 | 4 字节 | 请求序列号，用于匹配响应 |

请求和响应 body 分别为：

```text
请求：服务名长度 u32 | 服务名 | 方法名长度 u32 | 方法名 | 载荷长度 u32 | 载荷
响应：错误码 u32 | 错误文本长度 u32 | 错误文本 | 结果长度 u32 | 结果
```

body 最大为 1 MiB，包含长度字段和其他元数据，整帧最多为 `1 MiB + 12` 字节。字符串按长度读取，允许包含零字节。

TCP 是字节流。接收缓冲先等待完整头部，再依据 body 长度等待整帧；消费一帧后继续处理剩余数据。`Read()` 独立报告新增数据、EOF 和错误，允许一次读取同时得到数据和 EOF。客户端先解析新增数据：完整响应即成功；EOF 时仍缺少字节则报告连接关闭错误。可读与挂断同时发生时也先读取，不丢弃 EOF 前的数据。

### 7.2 如何扩展协议与校验完整性？

未启用传输变换时使用 CRPC 魔数和原始 body。启用后使用 CRP1 魔数识别传输版本，保留 12 字节固定头部，在 wire body 首字节记录压缩模式、实际压缩和加密标志。解码器拒绝未知标志、模式不匹配和长度超限。加密帧通过 GCM 认证头部与标志；未加密帧只有结构校验，没有 CRC 或密码学完整性认证。序列化类型仍由调用接口约定。

所有响应发送入口都应用相同大小限制。业务结果或错误文本超限时，转换为保留原序列号、清空结果的短协议错误响应，确保客户端仍可解析。请求超限则不能正常编码发送。

逻辑 body 和 wire body 均受 1 MiB 限制，加密和编码膨胀也计入 wire 上限。不能依靠压缩绕过逻辑长度限制；响应因变换膨胀超限也返回短协议错误。后续协议扩展应保留版本识别与严格配置校验。

## 8. 网络管理模块

### 8.1 使用 Reactor 还是 Proactor？如何支持并发？

[MessageCycle](../rpc_src/network/message_cycle.cc) 采用 Reactor：Linux 使用 epoll，socket 设为非阻塞，事件线程接收连接、读取并解析请求，再提交给线程池执行。业务完成后提交完整响应帧，事件线程负责发送、注册或取消写事件以及关闭 fd。代码保留 kqueue 分支，完整工具链与集成验证以 Linux 为主。

[Connection](../rpc_src/network/connection.cc) 的异步发送成功表示入队成功，不表示已写入 socket 或对端已收到。关键限制如下：

| 项目 | 当前限制或行为 |
| --- | --- |
| 每轮接入预算 | 最多 64 个连接，监听队列未清空时由下一轮继续处理 |
| fd 或 socket 资源不足 | 暂停监听读事件，按 100 毫秒起步、最长 1 秒退避恢复；已有连接继续处理 |
| 活动连接容量 | 由 `max_connections` 控制，达到上限时关闭新连接 |
| 每轮发送预算 | 64 KiB，防止单个慢连接长期占用事件线程 |
| 每轮读取预算 | 256 KiB |
| 单连接发送队列 | 最多 64 帧，且不超过 4 个最大帧的总字节数 |
| 短写或 `EAGAIN` | 保存偏移，启用 `EPOLLOUT`；队列发空后取消写事件 |
| 发送队列超限 | 拒绝入队并请求关闭连接 |
| 连接标识 | 排队操作携带连接对象或身份，避免 fd 复用误操作 |

macOS 分支对应使用 `EVFILT_WRITE`。唤醒通知去重，事件线程统一注销和关闭服务端 fd。工作线程无需同步等待慢客户端完成写入，慢读压力主要由每连接队列承担。

客户端没有负责刷新发送队列的事件循环，保留同步发送。发送使用单调时钟总期限覆盖短写、`EINTR` 和等待可写；接收另有期限。因此 `timeout_ms` 不是整个 RPC 调用共享的一次总预算。

当前服务端只有一个事件循环。线程池有助于隔离业务耗时，但性能仍受事件线程、业务负载和队列容量限制；`max_connections` 限制活动连接数，`listen_backlog` 单独控制内核监听队列。

## 9. 综合架构设计

### 9.1 核心模块如何协同？

一次示例调用经过以下步骤：

1. `RpcClient` 加载配置，建立独立 ZooKeeper 发现会话，查询实例并选址。
2. 客户端连接 TCP，将 JSON 参数编码为带序列号的请求帧并发送。
3. 事件线程拆分完整帧，检查令牌桶后投递线程池；工作线程解码、认证并解析请求，调用 `ServiceManager` 中的 `RpcService.Echo`。
4. 业务结果编码为响应帧，按配置压缩和加密，进入受限发送队列，由事件线程发送。
5. 客户端解码、认证，检查响应序列号与错误码，将结果反序列化返回，并更新该实例的熔断状态。

服务端启动时单独通过 `ServiceRegistry` 注册实例。日志贯穿各模块，Zstd 与 AES 按 transport 配置参与实际收发。对应入口为 [rpc_client.cc](../rpc_src/core/rpc_client.cc) 与 [servers_main.cc](../rpc_src/core/servers_main.cc)。

### 9.2 如何降低耦合并管理资源生命周期？

`Service` 统一业务入口，`ServiceManager` 管理服务名到处理器的映射；序列化器、协议、连接和注册分别负责载荷转换、帧格式、I/O 和实例所有权。分层使不同职责可独立测试，但全局负载均衡、线程池和日志仍共享进程状态，尚不是完整依赖注入架构。

并发生命周期使用拥有所有权的快照：[ThreadPoolSingleton](../rpc_src/thread_pool/thread_pool_singleton.h) 返回 `shared_ptr<ThreadPool>`，在单例锁内获取，锁外调用。销毁状态阻止新的懒初始化和提交，停止与等待也在锁外执行，因此业务任务读取统计不会被全局锁阻塞。

[ThreadPool](../rpc_src/thread_pool/thread_pool.cc) 将出队与执行中计数更新放在同一队列锁内；已退出 worker 的线程句柄在受同步保护的容器中移出，再锁外 join。回收与关闭共享所有权，防止重复 join。业务包装函数统计成功或失败，异常重新抛出并由 future 保留，worker 外层负责耗时和执行中计数。

关闭拆为 `RequestShutdown()` 与 `WaitForTermination()`：请求关闭拒绝新任务、解除暂停并排空已接收任务；无限等待使用带谓词的 `wait()`，有限等待使用单调时钟期限。超时返回 `false` 并保留运行任务所需资源，后续等待或析构回收。重复关闭协调执行，worker 不允许同步等待自身退出。

配置需区分实现入口。独立 [RpcClientConfig](../rpc_src/load_config/rpc_client_config.cc) 提供六个 setter，并以临时配置完成解析和校验后提交；端口范围为 1–65535，超时为正整数，重试次数为 0–100。非法 setter 参数抛出 `invalid_argument` 并保留当前值。实际 `RpcClient` 使用自己的配置加载及会话切换逻辑，并复用相同的严格数值校验。服务端及子配置通过候选对象完成校验后统一提交，注册节点列表按新配置替换；运行中的监听和线程池没有热更新机制。

客户端对象持有共享会话，AsyncCall 的后台任务捕获该会话，客户端对象销毁后任务仍拥有连接和配置。ServiceManager 的异步任务持有业务服务快照，并通过 `future<AsyncResult>` 返回自有结果，避免引用外部输出变量。

### 9.3 如何压测与定位泄漏？

[stress_test_client](../rpc_src/tools/stress_test_client.cc) 使用多个独立客户端和长连接，在起跑屏障后分配请求，调用 JSON Echo 并校验结果；类型错误、缺失或不匹配的消息计为失败，工作线程异常有独立处理边界。[stress_test.sh](../stress_test.sh) 可构建、启动服务端并清理它拥有的进程组；取消时传播终止信号并返回 130/143，超过可配置宽限期后强制结束未退出的子进程。配置、构建目录和日志的命令行路径在任何 `cd` 前按调用者目录规范化。

输出包含成功率、吞吐量、平均延迟和 P50/P95/P99。延迟样本包含成功与失败调用，吞吐量按完成调用计数；客户端初始连接准备不计入测试窗口。报告必须附上硬件、依赖版本、载荷大小、并发数、日志级别和错误率，仓库没有可直接外推的吞吐量承诺。

自动化验证分为协议与组件测试、受控交错并发测试、真实 TCP 测试、脚本回归和可选真实 ZooKeeper 集成测试。GoogleTest 目标通过 `gtest_discover_tests()` 注册到 CTest；并发测试使用 promise 或屏障控制交错。

内存错误与泄漏用独立 ASan/UBSan 构建及 LeakSanitizer 检查，数据竞争用独立 TSan 构建。真实测试覆盖发送背压、会话过期及重启恢复。测试报告应区分业务代码和第三方依赖的错误，并保留复现条件。可重复执行的命令见 [README 测试说明](../README.md#测试)。

### 9.4 如何控制流量和监控健康？

已有背压包括线程池待执行任务上限、响应队列上限、每轮 I/O 预算和帧大小限制。线程池统计提供队列长度、执行中任务数、成功与失败计数、平均任务耗时及 worker 句柄数量；日志记录生命周期和错误。这些背压与统计用于限制积压和排障。服务端还支持进程总配额的令牌桶，超限在入线程池前返回错误码 3005；requests_per_second 为 0 时关闭。

客户端按实例地址维护关闭、打开和半开探测状态。failure_threshold 默认 5，reset_timeout_ms 默认 5000；阈值为 0 时关闭熔断。实际远端建连、收发和协议失败计入连续故障；本地套接字创建、标志或选项初始化失败不改变实例熔断状态，有效业务错误或限流响应证明实例可通信，恢复健康计数。请求、响应类型与线格式不兼容时在建连和发送前拒绝，不影响实例故障计数。只有完整发现成功才清理消失实例的状态，节点读取部分失败时保留原有熔断历史；成功空目录允许清理全部历史。尚无按服务或方法的配额、基于延迟的熔断和独立监控导出接口。

### 9.5 有哪些高可用手段？

当前实现支持发现多个实例、轮询或随机分流、连接建立重试、注册会话过期恢复，以及 ZooKeeper 端点切换失败保留旧配置。真实集成测试验证会话过期和 ZooKeeper、TCP 服务重启后的恢复，但恢复期间仍可能出现调用失败，不能推导为无损切换。

生产级高可用还需要 ZooKeeper 集群部署、业务健康检查、明确故障摘除机制和请求幂等性。服务发现实时查询也会受 ZooKeeper 可用性影响；如加入缓存，需要定义缓存期限、更新顺序、失效和回退策略。当前没有这些缓存机制。

退出时，事件循环停止接收新请求，并最多等待 3 秒发送已接收请求的响应，然后关闭剩余连接。服务端随后请求线程池排空，先按配置等待，再继续等待任务退出，最后清理注册。普通 C++ 任务无法安全强制终止，因此有限等待不是取消承诺。

### 9.6 当前有哪些性能措施？

已采用非阻塞 I/O、长连接、业务线程池、批量事件处理、短写偏移、有限发送预算和队列容量；协议预估大小再分配，选址在全局锁外执行。线程池按需扩容，非核心线程空闲退出，后续提交或扩容时回收退出句柄，控制反复扩缩容后的资源积压。

这些措施解决具体阻塞、竞争和资源边界问题，并不自动保证高吞吐。下一步应通过负载剖析确定瓶颈，再评估多事件循环、缓冲区复用、异步日志或业务并行度。压缩与加密已接入链路，但端到端性能收益仍需分别测量；Protobuf 外层协议替换尚未实现。

## 10. Protobuf 补充问题

### 10.1 Protobuf 相比 JSON 的优势在哪里？

Protobuf 通过 schema 约束字段类型，用字段编号和二进制编码表达消息，并可生成多语言访问接口。JSON 可读性强，适合调试和通用接口。具体体积、速度与维护成本取决于数据和使用方式，不能仅凭格式判断。

项目提供两种适配器，但没有 JSON 与 Protobuf 的公平性能对比；压测工具使用 JSON Echo。选型时还需考虑可观察性、跨语言 schema 管理和跨版本兼容。

### 10.2 如何生成 C++、Java 和 Python 代码？

在仓库根目录执行，提前建立输出目录：

```bash
mkdir -p generated/cpp generated/java generated/python

protoc -I protos --cpp_out=generated/cpp protos/message.proto
protoc -I protos --java_out=generated/java protos/message.proto
protoc -I protos --python_out=generated/python protos/message.proto
```

生成代码仍需对应语言的 Protobuf 运行时；C++ 生成文件还要参与编译和链接。项目正常构建已由 CMake 调用依赖中的 `protoc`，将 C++ 文件写入构建目录的 `generated/`，无需手动生成到源码目录。[Protobuf C++ 入门](https://protobuf.dev/getting-started/cpptutorial/)

这些命令生成消息类型，不生成当前自定义 TCP 协议的完整客户端或服务端。

### 10.3 `json_name` 有什么用？

例如：

```proto
string service_name = 2 [json_name = "serviceName"];
```

`json_name` 控制该字段在 ProtoJSON 中的键名，便于对接已有 JSON 命名约定。它不改变 Protobuf 二进制字段编号或编码，也不影响项目普通类型的 nlohmann-json 映射。当前 `message.proto` 没有设置这一选项。[ProtoJSON 字段表示](https://protobuf.dev/programming-guides/json/)

### 10.4 Protobuf 如何存储对象？为什么通常更小？

Protobuf 二进制消息记录字段 tag 和字段值。tag 由 `(字段编号 << 3) | wire_type` 组成；整数常用 varint，字符串、bytes 和嵌套消息使用长度限定表示。接收端依赖 schema 解释字段类型，而不是在每条消息中重复保存完整字段名。[Protobuf 编码说明](https://protobuf.dev/programming-guides/encoding/)

相比 JSON，它通常减少字段名、引号和分隔符，小整数还能使用较少字节。普通 proto3 隐式存在字段的默认值通常不编码；显式存在性、消息字段和集合的规则有所不同。体积收益取决于字段编号、数值范围和载荷，JSON 中原本很短的数据未必显著变小。

例如负数 `int32` 的 varint 可能较长，需要按数据语义评估 `sint32` 等类型。项目没有此类编码调优或实际消息体积对比报告。

### 10.5 为什么 Protobuf 编解码通常较快？

生成代码知道字段类型，可以按 tag 和长度直接处理二进制数据，减少文本数字转换、字符串转义和字段名匹配。JSON 解析通常还需处理这些文本操作；收益会随解析器实现与消息结构变化。

Protobuf 同样存在内存分配、字符串复制和变长整数处理成本。对于很小的消息，RPC 网络与调度开销可能更显著。项目应在同一 schema、相同数据和编译选项下分别测量编解码耗时与端到端延迟，目前不能声称已验证固定倍数的提升。
