# CookRPC 项目面试问题参考答案

> 本文严格依据当前仓库源码回答。回答中明确区分三类内容：
>
> - **当前实现**：代码中已经存在并会实际执行的行为；
> - **实现边界**：代码提供了组件，但尚未接入完整 RPC 主链路，或当前实现存在明确限制；
> - **演进方案**：如果继续产品化，应该怎样补齐。面试时不要把演进方案表述成当前已经具备的能力。

## 1. 日志模块（spdlog）

### 1.1 为什么选择 spdlog 而不是 glog 或 log4cpp？它的异步日志机制如何实现？

#### 项目中的选择

项目在 `CMakeLists.txt` 中直接依赖 `spdlog`，日志封装位于 `utils/log_manager.h`。选择它主要是因为：

1. **C++11/17 友好、接入成本低**：项目是 C++17，spdlog 采用现代 C++ 接口，支持格式化占位符、编译期/运行期格式化，并且可以直接和项目已经使用的 `fmt` 配合。
2. **线程安全 sink 完整**：当前使用 `stdout_color_sink_mt` 和 `daily_file_format_sink_mt`，`_mt` 版本适合多个 RPC 工作线程同时写日志。
3. **sink 组合灵活**：同一个 logger 同时绑定控制台和文件 sink，代码中通过 `std::vector<spdlog::sink_ptr>` 完成组合，不需要业务代码分别写两套输出逻辑。
4. **日志级别和格式配置简单**：通过 `set_pattern` 统一输出日期、毫秒、级别、线程 ID 和正文；通过 `set_level` 控制最低级别。
5. **依赖和性能比较均衡**：相对 glog，spdlog 对全局初始化、sink 组合和嵌入式使用更轻量；相对 log4cpp，现代 C++ API、格式化和维护活跃度更适合本项目。

这不是说 glog 或 log4cpp 不能用。glog 在 Google 生态、崩溃处理和运维规范方面很成熟；log4cpp 的层级配置也比较完整。这里更看重的是教学项目的轻量性、可组合性和较低的使用门槛。

#### 当前实现是否是异步日志

**当前实现不是异步日志**。`Logger::Init` 创建的是普通 `spdlog::logger`，没有调用 `spdlog::async_logger`，也没有创建 `spdlog::details::thread_pool`。因此调用 `LOG_INFO` 等宏时，调用线程会同步执行 formatter 和各个 sink 的写操作。

如果要启用 spdlog 异步机制，典型实现是：

```cpp
auto thread_pool = std::make_shared<spdlog::details::thread_pool>(8192, 1);
auto logger = std::make_shared<spdlog::async_logger>(
    "main", sinks.begin(), sinks.end(), thread_pool,
    spdlog::async_overflow_policy::overrun_oldest);
```

业务线程只负责把日志消息复制/移动到有界队列，由后台线程完成格式化和 sink 写入。需要明确配置：队列长度、后台线程数、队列满时采用阻塞还是丢弃，以及进程退出时调用 `spdlog::shutdown()` 或等待队列排空。对于审计日志，不能无条件使用丢弃策略；对于 DEBUG 追踪日志，可以接受采样或丢弃。

### 1.2 多线程环境下如何避免日志竞争？如何配置日志滚动策略？

当前通过以下方式降低竞争风险：

- 使用 `stdout_color_sink_mt` 和 `daily_file_format_sink_mt`，sink 内部负责多线程互斥；
- 所有代码使用默认 logger 和统一宏，不在业务线程中自行操作文件句柄；
- `Logger::GetInstance()` 使用函数内静态对象，初始化本身是线程安全的；
- 日志格式中包含 `%t`，可以追踪线程来源；
- RPC 事件线程只负责读事件和投递任务，业务请求在线程池中执行，日志可能来自多个工作线程，因此 `_mt` sink 是必要的。

当前的滚动策略是**按天滚动**：`daily_file_format_sink_mt(log_file, 0, 0)` 表示每天 0 点生成/切换日志文件。日志基础文件名是 `../logs/cookrpc.log`，具体历史文件名由 spdlog daily sink 生成。

当前没有按文件大小滚动、压缩归档、最大保留天数或磁盘配额控制。如果生产环境需要大小滚动，可以改为 `rotating_file_sink_mt`，配置 `max_size` 和 `max_files`；也可以同时使用按天和按大小的自定义 sink，增加日志目录磁盘水位监控，避免磁盘打满导致业务线程同步写日志失败。

### 1.3 日志级别动态调整如何实现？如何保证日志写入不影响 RPC 性能？日志分级策略的实际应用场景是什么？

#### 当前级别行为

当前初始化时调用 `logger_->set_level(spdlog::level::trace)`，因此 TRACE 及以上日志都允许输出。代码中定义了 TRACE、DEBUG、INFO、WARN、ERROR、FATAL（映射到 `critical`）宏，并额外提供带 `[CLIENT]` 前缀的客户端宏。

当前**没有动态调整接口**，也没有从配置中心监听日志级别。要实现动态调整，可以增加：

1. 暴露 `Logger::SetLevel(spdlog::level::level_enum)`；
2. 将级别配置加入 JSON 或管理接口；
3. 由配置热更新线程解析后调用 `logger_->set_level`；
4. 修改级别时加 logger 自身支持的同步保护，禁止业务代码替换正在使用的 sink；
5. 多进程部署时通过 ZooKeeper/配置中心发布级别，实例收到变更后只更新本地 logger。

#### 性能保证

当前实现是同步日志，所以不能声称“日志绝不影响 RPC 性能”。可以做到的只是：

- 热路径避免无意义的高频 INFO；
- 使用 `SPDLOG_ACTIVE_LEVEL` 在编译期裁剪低级别日志（若构建系统启用该宏）；
- 将请求详细内容放在 DEBUG/TRACE，而不是默认 INFO；
- 生产环境将默认级别提高到 INFO/WARN；
- 使用异步 logger、有界队列和批量刷盘，将文件 I/O 从网络/业务线程移出；
- 对日志参数避免昂贵的字符串拼接，尽量让格式化只发生在日志真正启用时。

#### 分级策略

- **TRACE**：逐步跟踪协议状态、重试循环、事件循环细节，只用于短时问题定位。
- **DEBUG**：线程池取任务、发送响应、选择节点等调试信息。当前线程池和响应发送路径确实使用了 DEBUG。
- **INFO**：服务启动/停止、配置成功、ZooKeeper 会话连接、服务注册成功等正常生命周期事件。
- **WARN**：使用降级负载均衡策略、连接重试、日志/密钥使用临时配置、ZooKeeper 重连或节点已存在等可恢复异常。
- **ERROR**：请求帧非法、序列化失败、连接断开、业务处理失败、无法注册服务等当前操作失败。
- **FATAL/CRITICAL**：启动阶段无法加载配置、创建监听 socket、初始化线程池等导致进程无法继续的错误。项目中 `LOG_FATAL` 映射到 spdlog 的 critical，但它本身不自动终止进程，是否退出由调用方决定。

## 2. 负载均衡模块

### 2.1 实现了哪些算法？如何动态感知节点负载变化？

#### 已实现算法

负载均衡入口是 `LoadBalancer`，通过工厂映射支持 `random`、`round`、`weight` 三种字符串配置。

1. **随机**：`RandomLoadBalancer` 使用 `std::random_device` 初始化 `std::mt19937`，均匀随机选择候选地址。
2. **轮询**：`RoundRobinLoadBalancer` 使用 `std::atomic<size_t>` 计数器，`fetch_add(1) % instances.size()` 选择节点，多个线程调用时计数器不会发生数据竞争。
3. **加权轮询**：类名是 `WeightRoundRobinLoadBalancer`，但当前 `Select` 每次都创建全为 1 的权重数组，实际效果等同普通轮询。虽然类内有 `weights_` 和 `SetWeight`，但没有从配置或 ZooKeeper 读取权重，也没有实现动态权重。

因此，面试中应准确回答：**项目具备三种策略接口，真正可配置使用；当前加权策略尚未实现不同节点权重，默认是等权轮询。**

#### 当前的节点感知方式

客户端每次建立连接或重连时，通过 `ZkConnHandler::GetServer`：

1. 调用 `GetAllServers` 读取 ZooKeeper 命名空间下的子节点；
2. 对每个子节点调用 `zoo_get` 读取地址数据；
3. 将最新地址列表写入受 `servers_mutex_` 保护的 `servers_`；
4. 调用负载均衡器从地址列表选择一个实例。

这实现的是**服务实例拓扑变化感知**，不是 CPU、并发数、延迟等运行时负载感知。当前没有心跳指标、主动健康探测、连接数权重、EWMA 延迟或熔断状态。若要动态感知负载，应让实例定期上报权重/健康指标，或由客户端维护成功率、P95 延迟和并发数，再通过平滑加权轮询、最少连接或 EWMA 选择节点。

### 2.2 如何避免雪崩效应？如何与 ZooKeeper 协同实现服务发现？

#### 当前已经具备的保护

- 客户端配置 `retry_times`，连接失败时最多执行 `retry_times + 1` 次尝试；
- 每次尝试重新从 ZooKeeper 获取地址，不固守已经故障的地址；
- 失败重试间隔固定为 100ms，避免紧密自旋；
- 线程池有界队列，队列满时立即拒绝任务，返回 `kServiceUnavailable`，形成背压；
- RPC 帧、读缓冲和响应缓冲都有 1MB 上限，防止异常请求耗尽内存；
- 连接失败会清空旧连接和残留响应，避免旧响应污染下一次调用。

但这些措施还不能完全防止大规模雪崩。生产化还需要指数退避加随机抖动、按服务/租户限流、熔断半开、连接建立并发上限、失败实例临时摘除以及请求超时预算传递。

#### ZooKeeper 协同流程

服务端启动顺序是：初始化日志和配置、初始化线程池、注册 `RpcService`、创建并监听 TCP socket、将监听 socket 加入 epoll，最后初始化 ZooKeeper 并注册服务。这个顺序保证服务已经具备接收请求的能力后才对外发布。

`ServiceRegistry` 使用 `/cookrpc/<service_name>` 作为持久服务节点，并在下面创建值为 `ip:port` 的临时实例节点。客户端通过 `zoo_get_children` 枚举子节点，再读取每个节点内容，交给负载均衡器选择。临时节点会在 ZooKeeper 会话结束时自动删除，因此服务进程异常退出后不会长期留下地址。

## 3. 压缩模块

### 3.1 选择 zlib、Snappy 还是 zstd？如何权衡压缩率与速度？

项目实际选择的是 **Zstandard（zstd）**，封装在 `ZstdCompress` 中，支持字符串和二进制数据，并定义 1、3、7、19、22 五个压缩级别。

- **zlib**：兼容性最好、生态成熟，但同等压缩率下通常速度和解压性能不如 zstd，适合通用归档或已有 gzip/deflate 协议。
- **Snappy**：压缩/解压非常快、CPU 开销低，但压缩率相对低，适合极低延迟且带宽不紧张的场景。
- **zstd**：在低级别下接近 Snappy 的速度，在中高等级提供更好的压缩率，解压速度通常也很高，适合 RPC 中“减少网络字节数，同时控制 CPU 延迟”的平衡点。

本项目默认级别为 3，符合在线 RPC 的折中选择；级别 1 可用于极端低延迟，7/19/22 更适合带宽昂贵、CPU 充足或离线数据。实际选择不能只看压缩率，应基于真实 payload 测试压缩耗时、解压耗时、压缩后大小、CPU 使用率和端到端 P95/P99 延迟。

### 3.2 何时启用压缩？压缩失败如何处理？

`ZstdCompress` 本身没有阈值策略，也没有在 `RpcClient`、`MessageCycle` 或 `RpcProtocol` 请求链路中被调用。因此当前项目是**提供压缩组件，但 RPC 默认请求并不自动压缩**。

合理的接入方式是：

1. 先序列化 payload；
2. 小于阈值（例如 1KB 或通过压测确定的阈值）不压缩，因为压缩头和 CPU 成本可能超过节省的网络字节；
3. 大于阈值时压缩，只有 `compressed_size + 压缩元数据 < original_size` 才采用压缩结果；
4. 在协议扩展字段中记录压缩算法、原始长度和压缩长度；
5. 解压前校验原始长度上限，防止压缩炸弹。

当前 zstd 封装的失败语义是：返回 `false`，压缩目标清空；解压时通过 `ZSTD_getFrameContentSize` 获取原始大小，遇到未知大小、非法 frame 或库错误返回 `false`。调用方应将其转换为明确 RPC 错误，不能把未压缩数据误当成解压成功；如果产品允许降级，可以只在“压缩阶段失败且原文仍然可发送”时回退原文，但必须在协议中明确标志，不能让接收方猜测。

### 3.3 压缩与加密的顺序为何重要？你的设计顺序是什么？

正确顺序是：

```text
序列化 -> 压缩 -> 加密 -> 传输
接收 -> 解密 -> 完整性校验 -> 解压 -> 反序列化
```

原因是加密后的数据具有高熵，几乎不可压缩。如果先加密再压缩，不仅压缩率很差，还浪费 CPU。压缩后再加密也避免压缩侧信道暴露明文结构（但如果攻击者能控制明文并观察密文长度，仍需考虑长度泄露）。

当前仓库虽然同时提供 Zstd 和 AES-256-GCM 组件，但二者都没有接入 `RpcClient::PrepareRequest`/`ProcessResponse` 或服务端 `ProcessRpcRequest`，所以不能说当前已经执行了这个顺序。未来接入时，必须把压缩标志、原始长度、算法版本放进受认证的协议元数据，并在解密认证成功后再解压。

## 4. 加解密模块

### 4.1 使用对称 AES 还是非对称 RSA？

项目实际使用 **AES-256-GCM 对称加密**，基于 OpenSSL EVP API。每条消息生成 12 字节随机 nonce，输出 16 字节 GCM 认证标签，最终格式为：

```text
[版本 1 字节][nonce 12 字节][密文][GCM tag 16 字节]
```

再经过 Base64 编码，便于文本配置或传输。

AES 适合 RPC 大量数据的在线加密：吞吐高、延迟低、密文长度开销小。RSA 更适合密钥交换、签名或加密很短的数据，不适合逐请求加密大 payload。生产系统常见组合是 RSA/ECDH/证书体系保护会话密钥，再用 AES-GCM 加密业务流量。

### 4.2 密钥如何管理？如何防止重放攻击？加密算法性能如何测试？

#### 当前密钥管理

构造 `AesEncrypt` 时优先读取环境变量 `COOKRPC_MASTER_KEY_HEX`，要求 64 个十六进制字符，即 32 字节 AES-256 密钥；如果未设置，则用 `RAND_bytes` 生成仅在当前进程生命周期内有效的随机密钥，并打印 WARN。析构时调用 `OPENSSL_cleanse` 清理密钥内存。

这适合演示和避免源码硬编码，但临时密钥意味着进程重启后无法解密旧密文。生产环境应使用 KMS、Vault 或受权限控制的 Secret 管理系统，支持密钥版本、轮换、访问审计和最小权限；环境变量只是部署注入方式，不等于完整密钥管理系统。

#### 重放攻击

当前 AES-GCM 提供机密性和完整性，但**不能单独防止重放**：攻击者可以原样复制一份合法密文再次提交。当前协议有 `sequence_id`，但它只用于客户端匹配请求/响应，服务端没有持久化的去重窗口，也没有时间戳、随机请求 nonce 或过期时间校验，因此不能宣称已实现防重放。

完整方案应在认证数据中加入请求 ID、客户端身份、时间戳和有效期，并在服务端为每个客户端维护滑动窗口/已处理 ID 集合；对于严格一次语义，还要配合业务幂等键。重连或集群场景需要共享去重状态，或者采用带单调计数器的会话密钥。

#### 性能测试

应分别测试 AES-GCM 的加密、解密吞吐和端到端延迟：固定多种 payload（64B、1KB、64KB、1MB），预热 OpenSSL 上下文，测量每秒字节数、每次调用 CPU 时间、P50/P95/P99 和额外内存。还要对比开启/关闭加密时 RPC 吞吐、网络带宽和尾延迟，避免只测算法微基准。项目已有 `stress_test_client`，可扩展为 JSON/Protobuf、压缩/不压缩、加密/不加密的矩阵压测。

### 4.3 如何处理加密数据损坏或解密失败？

当前 `Decrypt` 会先严格校验 Base64、版本、最小长度和 nonce/tag 边界，再设置 GCM tag 并调用 `EVP_DecryptFinal_ex`。任何格式错误、密钥未初始化、密文被篡改或认证失败都会返回 `false`，并清空 `plaintext`。GCM 的 tag 校验必须在明文交给业务层之前完成；项目代码也明确把 `EVP_DecryptUpdate` 得到的内容视为“候选明文”，只有 Final 成功后才提交。

RPC 接入时，解密失败应返回统一的认证/协议错误并记录必要的计数指标，不能把原始密文当作明文重试，也不应把密钥、完整明文或密文写入日志。连续认证失败可触发连接关闭、客户端限流或安全告警。

## 5. 序列化与反序列化

### 5.1 为何选择 Protobuf、JSON？如何实现跨语言兼容？

项目通过 `SerializerManager` 同时支持 JSON 和 Protobuf：

- 对普通 C++ 类型使用 nlohmann/json；自定义类型通过 ADL 提供 `to_json/from_json`；
- 对继承 `google::protobuf::MessageLite` 的类型，只允许选择 PROTOBUF；
- 类型和线格式不匹配时直接返回 `false`，避免把 JSON 类型错误地按 protobuf 解析。

JSON 可读、调试方便、适合示例客户端 `RpcService.Echo`；Protobuf 是 schema 驱动的二进制格式，体积更小、解析更快、跨语言代码生成完整。

跨语言兼容的关键不是“都支持字符串”，而是：

1. 使用 `.proto` 定义稳定 schema；
2. 由对应语言的 `protoc` 生成 C++、Java、Python 等代码；
3. RPC 外层协议统一字节序、长度和错误语义；
4. payload 用协议中声明的序列化类型标识；
5. 不在不同语言间传递 C++ 对象内存布局、指针或编译器相关 ABI。

项目 `message.proto` 定义了 `RpcRequest`/`RpcResponse`，CMake 使用 `protobuf_generate(... LANGUAGE cpp)` 在构建目录生成 C++ 文件；独立脚本则调用 `protoc --cpp_out` 生成源码。

### 5.2 如何处理字段增删导致的版本兼容问题？自定义序列化如何优化性能？

#### Protobuf 兼容策略

当前 `.proto` 使用 proto3 字段编号。新增字段时使用新的 field number，旧客户端会忽略未知字段；旧字段删除后不能复用原编号，应该使用 `reserved` 保留编号和名称；字段类型不能随意变更，必要时新增字段并保留旧字段一段时间。枚举新增值时要让旧端能够安全处理未知枚举值。

JSON 当前是基于 `json.at(...).get_to(...)` 的严格映射，缺少字段是否兼容取决于 `from_json` 实现；项目测试中的 `JsonPayload` 直接要求 `request_id` 和 `method` 存在。因此 JSON 版本升级应使用可选字段、默认值和显式 `version`，不要直接假设所有字段都存在。

#### 性能优化

- Protobuf 使用 `SerializeToString`/`ParseFromString`，可以复用字符串缓冲区，避免不必要的中间 JSON DOM；
- 当前反序列化先创建同类型临时消息，成功后再 `Clear` 并合并，优先保证失败隔离；高吞吐场景可采用对象池/arena，但要严格管理生命周期；
- JSON 热路径应减少 `dump/parse` 次数，避免重复转换，必要时换用 SAX/零拷贝解析；
- 对大 payload 预分配 buffer，项目协议序列化已经使用 `reserve`，减少扩容；
- 自定义二进制格式只在 schema 稳定、性能收益明确且跨语言成本可接受时使用，并必须保留版本和边界校验。

## 6. ZooKeeper 节点注册

### 6.1 为何选择 ZooKeeper 而非 ETCD？临时节点和持久节点的区别？

当前项目选择 ZooKeeper C client，主要原因是：成熟的分布式协调语义、临时节点/会话模型天然适合服务实例注册，以及项目已经围绕 Watcher、会话状态和 `zoo_get_children` 实现了服务发现。

ETCD 基于 Raft、原生 gRPC/HTTP API、KV/Lease/Watch 体验更现代，云原生环境常更容易运维。若项目目标是 Kubernetes/云平台，ETCD 或直接使用现成服务注册组件也可能更合适。这里不能简单说 ZooKeeper “一定优于” ETCD，只能说当前代码已经围绕 ZooKeeper 实现，迁移会涉及客户端库、租约、watch 和注册语义重写。

当前节点层级是：

```text
/cookrpc                         持久根节点
└── <service_name>               持久服务节点
    └── <ip:port>                临时实例节点
```

持久节点不会因为会话断开自动删除，适合保存服务目录；临时节点绑定创建者 session，session 过期或连接关闭后由 ZooKeeper 自动删除，适合表示当前存活实例。当前 `ServiceRegistry::RegisterService` 使用 `ZOO_EPHEMERAL` 创建实例，父路径使用普通持久节点。

### 6.2 如何实现服务注册与发现？会话超时后如何恢复？

服务注册流程：服务端监听 socket 建好后，`ZkConnHandler` 初始化 ZooKeeper，`ServiceRegistry` 等待会话连接，再递归创建父路径，最后创建临时实例节点。节点数据是服务地址，重复创建 `ZNODEEXISTS` 被当作幂等成功。

服务发现流程：客户端初始化 ZooKeeper，调用 `GetAllServers` 获取命名空间子节点和节点数据，写入本地列表，再由负载均衡策略选择地址；连接失败时重新发现并建立 TCP 连接。

会话状态通过全局 Watcher 更新 `running_`/`is_connected_`，代码能识别 CONNECTED、CONNECTING、EXPIRED、AUTH_FAILED 等状态；`EnsureZkConnection` 会检查句柄并有限次等待，异常时 `CleanUp` 关闭句柄，下一次请求可懒初始化连接。

但当前恢复是不完整的：

- 没有实现对服务实例子节点的长期 watch，因此节点变化主要靠下一次 `GetServer` 主动拉取；
- session expired 后没有自动重新注册原有服务列表，只有清理后下次显式初始化/注册；
- ZooKeeper 连接恢复与服务注册恢复没有统一状态机。

生产化应在 CONNECTED/EXPIRED 事件后重新建立 session，重新创建父节点和临时实例；客户端应使用 watch 或定时刷新本地缓存；所有注册信息应可重放，且重新注册要幂等。

## 7. RPC 协议定义

### 7.1 如何设计协议头？如何解决粘包拆包？

当前协议头并不是问题中列出的 Magic/Version/MsgID/Length 四字段，而是三个 32 位网络字节序字段：

```text
magic_number   4 字节，固定为 ASCII “CRPC” 的 0x43525043
message_length 4 字节，body 长度，不含 12 字节头
sequence_id    4 字节，请求/响应匹配 ID
```

请求 body：三个“4 字节长度 + 原始字节”的字段，依次是 service、method、payload；响应 body：error code、error message 字段和 result data 字段。字符串使用 `std::string`，因此 payload 可以包含 `\0`。

魔数用于快速判断协议类型和错位；长度用于帧边界；sequence_id 用于匹配响应。当前没有显式 Version、MsgID 字段和 CRC 字段，sequence_id 承担的是请求编号而不是全局消息类型。

TCP 是字节流，项目通过 `Connection::read_buffer_` 累积数据：

1. 至少收到 12 字节后读取 magic 和 body length；
2. 若尚未收到完整 `12 + body_length`，保留缓冲区等待下一次 epoll 读事件；
3. 收到完整帧后交给 `RpcRequest::Deserialize`，处理完从缓冲区移除；
4. `while` 循环继续处理同一次 recv 中携带的多帧数据。

客户端响应路径也有 `pending_response_data_`，支持半帧、多帧和总超时。发送侧 `Connection::SendInBuffer` 处理短写和 EAGAIN。因此粘包/拆包不是依赖一次 `recv` 对齐，而是依赖长度字段和累计缓冲区。

### 7.2 协议扩展性如何保证？如何校验数据完整性？

当前扩展性主要来自：字段采用长度前缀而不是固定 C struct；整数明确使用网络字节序；请求和响应解析完成后才一次性提交到对象；长度计算使用 `uint32_t` 上限检查；未知尾随数据会被拒绝，避免静默吞掉协议错误。

但是当前协议没有显式 version、flags、压缩算法、加密算法或 CRC。尤其 `ReadHeader` 要求 body 长度与输入剩余长度精确一致，向头部追加字段需要同步修改解析逻辑，不能直接把它当作完整 TLV 协议。

完整演进方案可以将头部扩展为：`magic、version、flags、header_length、body_length、request_id、checksum`，保留 flags/扩展 TLV 区域。旧版本根据 `header_length` 跳过未知扩展；新增字段放入 TLV，不改变已有字段位置。

当前完整性校验依靠：长度边界检查、魔数校验、字段长度校验以及 TCP 校验和。项目**没有实现 CRC 校验**。如果要增加 CRC32C，应让发送方对头部（排除 checksum 字段）和 body 计算校验值，接收方在反序列化/业务处理前验证；安全场景下 CRC 只能发现随机损坏，不能防篡改，必须由 AES-GCM tag 或数字签名提供密码学完整性。

## 8. 网络管理模块

### 8.1 使用 Reactor 还是 Proactor？如何实现高并发？

当前实现是 **Reactor**：Linux 下使用 epoll，macOS 下使用 kqueue；事件循环等待“可读”等就绪事件，再由用户态调用 `recv/send` 完成实际 I/O。Proactor 则由系统/异步 I/O 框架完成操作后回调，当前项目没有使用 io_uring、Windows IOCP 或异步文件/网络完成通知。

高并发链路如下：

1. 监听 socket 非阻塞并注册到 epoll；
2. `epoll_wait` 一次获取最多 1024 个事件；
3. 监听 fd 排空 accept 队列，客户端 fd 设置非阻塞、TCP_NODELAY、SO_KEEPALIVE；
4. `Connection` 为每个连接维护读/写缓冲，处理短读、短写、EAGAIN、EINTR；
5. 事件线程解析完整 RPC 帧后，把业务处理投递到有界线程池，避免慢业务阻塞 epoll 循环；
6. `ConnectionManager` 用线程安全 map 管理 fd 到连接对象的生命周期；
7. 线程池按 core/max threads 扩容，使用优先级队列，并在队列满时快速拒绝任务形成背压。

当前是单个 `MessageCycle` 事件循环，业务并发主要来自线程池；还没有多 Reactor、端口复用后的每核事件线程、写事件订阅优化或连接级限流。进一步扩展可以采用主 Reactor 负责 accept、多个从 Reactor 负责连接读写，并将业务线程池与 I/O 线程池隔离。

## 9. 综合架构设计

### 9.1 整个 RPC 框架有哪些核心模块？怎样协同？

调用链可以概括为：

```text
客户端配置
  -> ZooKeeper 服务发现
  -> 负载均衡选择 ip:port
  -> 非阻塞 TCP 连接
  -> 序列化 payload（JSON/Protobuf）
  -> RpcRequest 协议封帧
  -> Connection 发送
  -> 服务端 epoll/Reactor 收帧
  -> 线程池执行 ServiceManager
  -> RpcService 业务处理
  -> RpcResponse 封帧发送
  -> 客户端按 sequence_id 校验并反序列化
```

核心模块包括：

- 配置模块：读取服务端、客户端、线程池和注册节点 JSON；
- 注册发现模块：`ServiceRegistry`、`ZkConnHandler`；
- 负载均衡模块：随机、轮询、等权“加权”策略；
- 网络模块：`CreateSocket`、`MessageCycle`、`Connection`、`ConnectionManager`；
- 协议模块：RpcHeader、请求/响应帧编解码；
- 序列化模块：JSON/Protobuf 适配器和 `SerializerManager`；
- 业务模块：`Service` 抽象、`ServiceManager`、示例 `RpcService`；
- 并发模块：支持优先级、有界队列、统计和优雅关闭的线程池；
- 横切模块：spdlog、Zstd、AES-GCM、压力测试工具。

### 9.2 如何保证模块间低耦合？

- 网络层只依赖 `RpcRequest/RpcResponse` 和回调，不知道具体业务类；
- 业务通过 `Service` 抽象注册到 `ServiceManager`，网络层通过服务名/方法名分发；
- 序列化通过 `SerializerManager` 和 `SerializeType` 分派，客户端调用不直接依赖 JSON/Protobuf 细节；
- 负载均衡通过抽象基类和工厂创建，策略可替换；
- ZooKeeper 封装在 `ZkConnHandler`/`ServiceRegistry`，客户端只拿到地址字符串；
- 连接生命周期由 `ConnectionManager` 统一管理，业务回调持有 `shared_ptr`，避免手工释放 fd；
- 配置对象提供 getter，入口程序不直接操作内部字段。

仍可改进的地方是：当前大量模块使用全局单例，测试隔离和多实例部署不够灵活；可以通过依赖注入传入注册中心、负载均衡器、时钟和日志接口，并定义明确的错误类型和取消令牌。

### 9.3 如何测试性能？如何定位内存泄漏？

#### 9.3.1 性能测试

项目自带 `stress_test_client` 和 `stress_test.sh`：每个压测线程持有一个独立 `RpcClient` 和长连接，原子分配请求编号，统计成功率、吞吐、平均延迟、P50/P95/P99/最大延迟。脚本可选择构建、启动本地服务端、配置并发连接数/请求数/payload 大小。

正式压测应分层：

1. 协议/序列化微基准：JSON 与 Protobuf 的大小、CPU、延迟；
2. 压缩/加密微基准：不同 payload 和级别；
3. 单机 RPC 基准：固定连接数，逐步增加 QPS；
4. 多实例基准：观察 ZooKeeper 发现和负载均衡分布；
5. 故障压测：服务重启、节点摘除、ZooKeeper 断连、线程池队列打满。

关注 QPS、成功率、端到端 P50/P95/P99、连接建立耗时、CPU、RSS、上下文切换、线程池队列深度、活动线程数、网络带宽和错误码比例。

#### 内存泄漏定位

- Debug 构建使用 AddressSanitizer/LeakSanitizer：`-fsanitize=address,leak,undefined`；
- 使用 Valgrind Memcheck 做长时间运行和启停循环；
- 用 heaptrack/perf 观察分配热点；
- 重点覆盖连接建立/断开、异常协议帧、线程池超时关闭、ZooKeeper session 过期和重复初始化；
- 检查 fd 数量、ConnectionManager 活跃连接数、线程数、日志文件句柄和 ZooKeeper 句柄是否在反复压测后回落。

代码本身已经大量使用 RAII、`unique_ptr`、`shared_ptr`、容器和析构函数；但 RAII 不能替代工具验证，尤其要警惕回调循环引用、线程未 join、外部库句柄和异常路径。

### 9.4 如何实现流量控制？如何监控系统健康状态？

当前最接近流控的是线程池有界队列：`max_queue_size` 达到上限时 `Enqueue` 返回无效 future，网络层立即发送 `kServiceUnavailable`。这属于**并发/队列背压**，不是完整的 QPS 限流或熔断。

可继续实现：

- 令牌桶/漏桶按服务、方法、租户或 IP 限制 QPS；
- 并发信号量限制单个方法在途请求数；
- 超时、连续失败或 P99 超阈值触发熔断；
- 半开状态只放少量探测请求，恢复后关闭熔断；
- 连接数、请求体大小、队列等待时间和下游超时统一纳入预算；
- 在负载均衡器中摘除熔断实例，并设置恢复冷却时间。

当前健康状态主要通过日志和返回值体现：ZooKeeper session 状态、连接状态、线程池 Stats、RPC 错误码、连接数和压测结果。生产环境应增加 Prometheus/OpenTelemetry 指标、健康检查 RPC、就绪/存活探针、结构化日志和 trace_id；健康检查至少要区分进程存活、线程池可接收任务、ZooKeeper 可用和业务依赖可用。

### 9.5 有哪些手段保证高可用？

当前已经具备的基础能力：

- ZooKeeper 临时节点表示实例存活，异常退出后自动摘除；
- 客户端从注册中心重新发现并重连；
- 多种负载均衡策略可分散请求；
- 服务端线程池、连接管理和优雅停机降低单个请求故障影响；
- socket keepalive、连接超时和有限重试避免永久阻塞；
- 请求/响应序列号和严格帧校验避免错配。

但真正高可用还需要至少两个服务实例、ZooKeeper 集群而不是单机 `localhost:2181`、跨可用区部署、健康检查摘除、指数退避、熔断降级、幂等重试、容量预留和发布回滚。当前配置示例只有一个注册节点，不能据此声称已经实现集群级高可用。

### 9.6 用到了哪些性能调优方法？

代码中已有的优化包括：

- epoll/kqueue 非阻塞事件循环，避免每连接一个阻塞线程；
- 业务请求从事件线程投递线程池，避免慢业务阻塞网络事件；
- `TCP_NODELAY` 降低小 RPC 报文等待；
- `SO_KEEPALIVE` 发现长期失效连接；
- 读写缓冲处理短读/短写，减少错误重试；
- 协议序列化前 `reserve`，减少字符串反复扩容；
- Protobuf 使用二进制编码，JSON 只在可读性优先的场景使用；
- 线程池有界队列、按积压动态增加非核心线程、空闲回收；
- 压测每个工作线程独享连接和延迟数组，避免热路径全局锁；
- 关闭时等待在途任务完成，减少不必要的重试和资源抖动。

还应通过 profile 决定是否启用压缩、加密、异步日志、连接池、多 Reactor、批量发送和内存池，不能仅凭直觉优化。优化目标应以 P99、CPU、内存和错误率共同衡量。

## 10. 其他 Protobuf 问题

### 10.1 protobuf 相比 JSON 的优势

1. **体积更小**：字段用数字编号编码，字段名通常不重复写入；整数使用 varint，较小数值只占 1~2 字节。
2. **解析更快**：不需要词法分析、字符串比较和通用 JSON DOM 构造，生成代码直接按字段 tag 解析。
3. **强 schema**：`.proto` 明确字段类型、编号和可选语义，编译期生成类型安全 API。
4. **跨语言**：同一个 schema 可生成 C++、Java、Python、Go 等代码。
5. **演进兼容**：新增字段可被旧端忽略，旧端字段可被新端使用默认值，前提是遵守 field number 和类型兼容规则。
6. **二进制字段友好**：`bytes` 不需要 Base64，适合 RPC payload。

JSON 的优势是可读、调试和浏览器生态好，因此项目保留双格式，而不是试图让 Protobuf 取代所有 JSON 使用场景。

### 10.2 protobuf 怎么编译成 C++、Java、Python 代码？

流程都是安装对应语言插件并调用 `protoc`：

```bash
# C++
protoc --proto_path=protos --cpp_out=generated protos/message.proto

# Java
protoc --proto_path=protos --java_out=generated protos/message.proto

# Python
protoc --proto_path=protos --python_out=generated protos/message.proto
```

C++ 生成 `.pb.h/.pb.cc`，需要链接 protobuf runtime；Java 生成 Java 类，通常配合 Maven/Gradle 的 protobuf 插件；Python 生成 `*_pb2.py`，运行时安装 protobuf 包。

本项目的 CMake 将 `protos/message.proto` 作为 `rpc_common` 的构建输入，调用 `protobuf_generate` 并把输出放在构建目录 `generated`，避免把特定机器生成的文件长期留在源码树。`protos/compile_proto.sh` 是手工生成 C++ 源码的辅助脚本。

### 10.3 protobuf 可以自定义 JSON tag，这个有什么用？

Protobuf 的 JSON 名称通常来自字段名的 lowerCamelCase 映射，也可以使用 `json_name` 指定 JSON 输出/解析时的字段名，例如：

```proto
string service_name = 2 [json_name = "serviceName"];
```

它只影响 **Protobuf JSON 映射**，不改变二进制编码中的 field number，也不改变 C++ 生成 API 的字段语义。用途包括兼容已有 REST/前端字段命名、统一 camelCase/snake_case、平滑迁移旧 JSON API。需要注意：项目当前的 JSON 序列化器是 nlohmann/json，主要依赖 C++ 类型的 `to_json/from_json`，并不是 `google::protobuf::util::MessageToJsonString`，所以在项目当前 JSON 路径中，`json_name` 不会自动替代自定义 C++ JSON key。

### 10.4 同一个对象用 JSON 和 protobuf 存，protobuf 怎么存？为什么体积更小？

以 `message.proto` 中的请求为例：

```proto
uint64 request_id = 1;
string service_name = 2;
string method_name = 3;
bytes payload = 4;
```

Protobuf 二进制通常按“字段 tag + 字段值”写入：tag 是 `(field_number << 3) | wire_type`。字符串/bytes 使用 length-delimited 编码：先写长度，再写原始 UTF-8/二进制内容；`uint64` 使用 varint，小数值按 1 字节或少量字节保存。没有值的 proto3 标量字段通常不输出默认值。

JSON 则会重复保存字段名和标点，例如 `{"request_id":42,"service_name":"..."}`，数字也通常以 ASCII 文本保存，二进制 bytes 还可能需要 Base64。因此同一个对象大多数情况下 protobuf 更小。但如果对象字段很少、字符串很短，固定 tag/长度前缀和 protobuf runtime 开销也可能让差距不明显；protobuf 并不是对所有数据都必然更小。

### 10.5 protobuf 为什么序列化和反序列化比较快？

- schema 在编译期确定，生成代码知道每个字段的类型和编号，不需要运行时反射推断；
- 二进制 tag/varint/length-delimited 解析比 JSON 的字符扫描、转义处理和数字文本转换简单；
- 默认值字段可以省略，减少要写入和解析的字节；
- `bytes` 直接传输原始数据，不需要 JSON 字符串转义或 Base64；
- C++ runtime 可以直接写入连续 `std::string`，项目的 `ProtobufSerializer` 只调用 `SerializeToString`；
- 反序列化时项目先创建同类型临时消息，成功后再提交，牺牲少量临时分配换取失败安全；高吞吐场景可进一步使用 arena、对象池和缓冲区复用。

速度优势不是无条件的：消息很小、CPU 不紧张时 JSON 也可能足够；如果频繁构造 JSON DOM、重复拷贝大字符串，JSON 会明显变慢。最终仍应在项目真实 payload、并发度和编译优化选项下做基准测试。

## 面试时的总括性结论

这个项目是一个教学型 C++17 RPC 框架，已经完整展示了 TCP/epoll、线程池、服务注册发现、协议分帧、JSON/Protobuf 序列化和基础故障处理。需要特别诚实说明的边界是：

1. spdlog 当前是同步 logger，不是异步 logger；
2. Zstd 和 AES-256-GCM 已封装并有单元测试，但尚未接入 RPC 主链路；
3. 负载均衡支持随机、轮询和等权实现的 weight 策略，尚无真实动态权重或一致性哈希；
4. ZooKeeper 使用临时实例节点，但 session 过期后的自动重新注册和长期 watch 仍需完善；
5. RPC 头部有 magic、body length、sequence_id 和严格边界校验，但没有 version、CRC、压缩/加密 flags；
6. 流量控制目前主要是线程池有界队列背压，还不是完整的令牌桶限流和熔断系统。

准确讲清这些已经实现和未实现的边界，比笼统声称“支持所有企业级能力”更符合专业面试表达。
