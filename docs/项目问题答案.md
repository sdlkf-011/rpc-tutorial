本文按 [项目问题](项目问题.md) 的章节、编号和原始题目逐项回答，共 29 题。每题先给可以直接口述的“面试回答”，再给被追问时的展开。第一人称表述用于练习，面试时应按自己实际负责的工作调整。

当前实现使用现在时；尚未实现的方案使用“如果扩展，我会”。文中的默认参数是当前配置或代码选择，不代表已通过基准测试证明最优。运行命令与完整配置见 [README](../README.md)。

## 1.日志模块（spdlog）

### 1.1 为什么选择 spdlog 而不是 glog 或 log4cpp？它的异步日志机制如何实现？

**面试回答：**

我选择 spdlog，主要考虑接口简洁、支持类型安全的格式化，而且能通过 sink 组合控制台和文件输出，与项目使用的 fmt 比较容易集成。glog、log4cpp 也能完成日志功能，我没有做过同条件性能对比，因此这里的选型依据是项目需求和集成成本。

项目当前使用同步 logger，日志由调用线程写入。如果改成异步日志，我会使用 spdlog 的异步 logger：业务线程把记录放入有界队列，后台线程取出记录并写入 sink，让业务线程减少等待磁盘 I/O 的时间。

**追问：异步日志能保证不阻塞、不丢失吗？**

不能同时无条件保证。队列满时，阻塞会增加业务延迟，丢弃则会损失日志。我会按日志用途选择策略，记录丢弃数量，并在退出时先停止产生日志的业务线程，再完成队列处理和日志系统关闭。异步化也仍有参数计算、复制和入队成本。

代码：[log_manager.h](../utils/log_manager.h)。机制参考：[spdlog 异步日志](https://github.com/gabime/spdlog/wiki/Asynchronous-logging)。

### 1.2 多线程环境下如何避免日志竞争？如何配置日志滚动策略？

**面试回答：**

项目的控制台和文件分别使用 `stdout_color_sink_mt`、`daily_file_sink_mt`。同一个 sink 内部用互斥锁保护写入和文件状态，避免线程并发写入破坏输出。线程安全仍然有锁竞争；同步写入时，业务线程还可能等待文件 I/O。

文件日志使用日期文件名，零点之后的第一条日志触发切换，写入新的 `cookrpc_YYYY-MM-DD.log`。logger 在启动工作线程前初始化；单例的构造安全，并不代表可以并发调用 `Init()` 重新配置。

**追问：如何按大小滚动、限制保留时间？**

如果增加大小滚动，我会换成 `rotating_file_sink_mt`，配置单文件阈值和历史文件数。daily sink 也能限制每日文件数量，但“保留 7 个文件”不等于严格清理 7 天前的全部日志。严格按天过期时，我会由后台任务扫描本服务的归档文件，按日期清理并排除当前文件。

**追问：多进程和集中采集怎么处理？**

`_mt` 的锁不能协调不同进程。当前客户端和服务端可能写到同一日期文件；完善时我会按角色和实例区分文件。集中采集时输出结构化日志，由独立 Agent 跟踪文件和读取位置、缓冲并转发，同时明确采集故障时的容量限制。这些扩展当前尚未配置。

代码：[log_manager.h](../utils/log_manager.h)。接口参考：[spdlog sinks](https://github.com/gabime/spdlog/wiki/Sinks)。

### 1.3 日志级别动态调整如何实现？如何保证日志写入不影响 RPC 性能？日志分级策略（Debug/Info/Warn/Error）的实际应用场景是什么？

**面试回答：**

我会区分编译级别和运行时级别。`SPDLOG_ACTIVE_LEVEL` 决定哪些日志宏编译进程序，`set_level()` 决定运行时输出哪些日志。项目初始化时设为 TRACE，但没有显式配置编译级别；按 spdlog 默认配置，DEBUG 和 TRACE 宏会被编译掉，运行时调低阈值也恢复不了。

当前还没有动态配置入口。如果增加，我会在配置重载或管理接口中校验级别，再更新已有 logger 的阈值，不重新初始化整个日志系统。日常运行使用 INFO，排障时临时开启 DEBUG，并考虑自动恢复，防止长时间大量输出。

| 级别 | 面试时可以举的项目例子 |
| --- | --- |
| TRACE | 每轮读写字节数、缓冲区变化等高频细节 |
| DEBUG | 选中的实例、请求序列号、响应入队、阶段耗时 |
| INFO | 启动、注册成功、配置变更、正常退出 |
| WARN | 可以重试的连接异常、策略回退、熔断状态变化 |
| ERROR | 重试耗尽、请求处理失败、非法协议 |
| FATAL / CRITICAL | 必需配置错误、监听失败等无法继续提供服务的问题 |

**追问：如何控制开销？**

我不会承诺日志完全没有性能影响，而会减少热路径输出，对重复错误限频、对高频细节采样，避免每条日志刷新文件。昂贵的字符串构造先用 `should_log()` 判断；当前 `CLIENT_*` 宏内有一次提前的 `fmt::format()`，运行时过滤不能消除这部分计算，也可以进一步简化。

如果同步写入影响事件线程，我会评估有界队列的异步日志，并比较同一负载下的吞吐量、CPU 和 P99 延迟。错误级别按影响划分：重试中可以记 WARN，最终失败记 ERROR；正常业务拒绝不必一律记 ERROR。`LOG_FATAL` 只映射到 critical，不会自动退出进程。

代码：[log_manager.h](../utils/log_manager.h)。编译过滤与刷新机制参考：[spdlog FAQ](https://github.com/gabime/spdlog/wiki/FAQ)。

## 2.负载均衡模块

### 2.1 实现了哪些负载均衡算法（轮询/加权/一致性哈希）？如何动态感知节点负载变化？

**面试回答：**

目前真正实现的是随机和轮询。随机在候选实例中选取一个，轮询使用原子递增索引分配选择次数。代码也有 `weight` 策略入口，但所有实例的权重实际都是 1，所以当前是等权轮询，没有实现非等权分配或一致性哈希。

当前没有采集节点 CPU、队列长度或延迟来动态调整权重。如果扩展，我会周期性采集这些指标，平滑计算权重并发布不可变快照，选址时读取快照，避免每次调用再去远程查询负载。还要设置过期时间和恢复探测，防止指标抖动造成流量来回切换。

**追问：并发选址和长连接有什么需要注意的？**

全局锁只用于取得策略的共享指针，实际选址在锁外执行；随机数引擎由策略内部加锁，轮询索引用原子操作。当前策略是进程内共享的。客户端在建连或重连时选址，连接建立后继续复用，所以轮询分配的是选址次数，不能保证各实例收到的请求量绝对相同。

代码：[load_balancer.cc](../rpc_src/conn_balancer/load_balancer.cc)、[weight.h](../rpc_src/conn_balancer/weight.h)。

### 2.2 如何避免雪崩效应？如何与 Zookeeper 协同实现服务发现？

**面试回答：**

我把故障隔离分在两端：客户端按实例维护熔断状态，连续通信失败达到阈值后暂时避开该实例，冷却后只允许一次探测；服务端通过令牌桶、有限任务队列和响应队列控制积压，避免流量超过处理能力后无限消耗资源。

发现时，客户端通过自己的 ZooKeeper 会话读取服务目录下的实例和地址，过滤暂不可用的候选实例，再交给负载均衡选择。当前是需要选址时查询，没有常驻实例缓存和持续子节点 watch。每个客户端的发现会话独立，熔断状态也在客户端会话内维护。

**追问：会不会因为重试把故障放大？**

有这个风险。当前只对连接建立做有限重试，失败间隔固定为 100 毫秒；已经发送的业务请求不会自动重试。扩展时我会加入退避、抖动和总重试预算，并要求业务重试具备幂等性。收到有效业务错误或限流响应，说明远端可通信，不计为实例通信故障。

代码：[rpc_client.cc](../rpc_src/core/rpc_client.cc)、[zk_conn_handler.cc](../rpc_src/conn_balancer/zk_conn_handler.cc)、[request_controls.cc](../rpc_src/core/request_controls.cc)。

## 3.压缩模块

### 3.1 选择 zlib、Snappy 还是 zstd？如何权衡压缩率与速度？

**面试回答：**

这几种算法都可以作为候选：zlib 的兼容生态成熟，Snappy 通常偏重低延迟和吞吐，Zstd 提供较灵活的速度与体积取舍。项目使用 Zstd，组件封装了多个等级，当前 RPC 链路默认使用 3 级。不过我没有做过这三种算法在相同业务数据上的对比，不能据此声称 Zstd 一定最快。

我的判断标准是节省的传输时间能否抵消压缩、解压和额外排队的时间。网络带宽紧张、大消息和重复数据较多时更值得尝试；小消息、CPU 紧张或数据已经压缩时，收益可能很小。最终选择要满足 RPC 的延迟目标，不能只看压缩后大小。

**追问：怎么验证等级和阈值？**

我会使用相同硬件、并发和真实载荷，对比不压缩以及 Zstd 1、3、7 级，记录体积、压缩与解压耗时、CPU、吞吐量和 P99 延迟，再调整阈值。当前 3 级和 1 KiB 阈值是初始选择，没有实测依据可以证明最优；压缩后更小也不代表已经赚回压缩的 CPU 成本。

代码：[zstd_compress.h](../rpc_src/compress_data/zstd_compress.h)、[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)。算法取舍参考：[Zstd 官方说明](https://github.com/facebook/zstd#benchmarks)。

### 3.2 如何判断何时启用压缩（如数据阈值）？压缩失败如何处理？

**面试回答：**

项目通过 `transport.compression` 开启压缩模式，再根据 body 大小决定是否实际压缩。当前阈值是 1024 字节，达到阈值才尝试，并且只有输出更小时才使用压缩数据。协议标志区分“启用了压缩模式”和“这一帧实际压缩”，接收方按标志决定是否解压。

压缩函数通过布尔值报告结果；失败时不能继续消费输出。当前编码失败会使发送操作失败，不会悄悄改成其他协议模式。压缩成功但没有体积收益时，可以发送未压缩 body，这是协议允许的正常路径。

**追问：怎样防止压缩包导致内存膨胀？**

我分别限制逻辑 body 和线上 body，二者都不能超过 1 MiB。解压前先读取声明的原始大小，确认不超限再分配；未知大小、非法帧、解压失败都拒绝。响应因大小或编码膨胀超限时会尝试转换成保留原序列号的短错误响应，不能依靠压缩绕过逻辑大小限制。

代码：[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)、[zstd_compress.cc](../rpc_src/compress_data/zstd_compress.cc)。

### 3.3 压缩与加密的顺序为何重要？你的设计顺序是什么？

**面试回答：**

项目的顺序是先序列化，再按配置压缩，最后加密与认证。接收方按相反顺序，先验证并解密，再解压，最后解析业务数据。原因是压缩依赖数据的重复性，而密文通常很难再压缩；先加密再压缩往往只有成本、没有明显体积收益。

认证必须先于解压和业务解析。项目把帧头、变换标志和请求响应方向也纳入认证，避免只改长度、序列号或方向就绕过校验。没有启用某项变换时，跳过对应步骤。

**追问：先压缩再加密就一定安全吗？**

还要考虑长度泄露。如果攻击者能控制部分明文，并观察包含秘密数据的压缩后长度，可能形成侧信道。扩展敏感业务时，我会评估禁用这类消息的压缩，或者分离秘密数据与可控输入，不能只因为密文不可读就忽略长度信息。

代码：[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)。

## 4.加解密模块

### 4.1 使用对称加密（AES）还是非对称加密（RSA）？

**面试回答：**

项目的数据传输使用 AES-256-GCM，通过 OpenSSL EVP 接口实现。对称加密适合处理持续传输的业务数据，GCM 同时提供机密性和认证能力，接收方可以检查密文和附加元数据是否被篡改。

当前两端通过显式配置共享密钥，没有使用 RSA，也没有证书认证和密钥协商。如果扩展为生产环境的安全传输，我会优先考虑成熟的 TLS 实现，由握手建立会话密钥，再用对称算法传输数据，避免自行拼装完整安全协议。

**追问：nonce 和密文如何组织？**

每条消息使用 12 字节随机 nonce，附带 16 字节认证 tag。同一密钥下必须避免 nonce 重用，随机数来自 OpenSSL 的 `RAND_bytes()`，不是普通伪随机引擎。当前输出把版本、nonce、密文和 tag 拼接后再做 Base64；Base64 是编码，会增加体积，本身不提供加密。

代码：[aes_encrypt.cc](../rpc_src/encrypt/aes_encrypt.cc)、[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)。

### 4.2 密钥如何管理？如何防止重放攻击？加密算法性能如何测试？

**面试回答：**

RPC 加密从环境变量 `COOKRPC_MASTER_KEY_HEX` 读取 64 个十六进制字符，解析成 32 字节共享密钥。两端需要注入相同的值，不把密钥写进源码或配置文件，也不记录到日志。启用加密但密钥缺失或格式错误时，配置加载失败，不会自动退回明文。

防重放需要单独设计，GCM 只能验证真实性，不能判断一条真实消息是否被再次发送。当前加密连接按序列号规则拒绝零值、重复和倒退请求，并允许正常计数回绕；这只是连接内的限制，没有跨连接的持久去重或挑战机制。

**追问：如何进一步完善密钥和重放保护？**

环境变量只是当前注入方式，不能代替密钥管理系统。扩展时我会使用受控的秘密存储，限制权限，定义密钥版本和轮换流程；安全传输优先使用 TLS。业务层的重复提交还需要幂等键与去重存储，连接内序列号不能保证业务只执行一次。

**追问：性能怎么测？**

我会分开测纯加解密和端到端 RPC，覆盖不同消息大小与并发，记录吞吐量、CPU、P95/P99 延迟及密文膨胀。当前实现还需要计入随机数生成、上下文创建和 Base64 的成本。已有测试覆盖功能与篡改场景，但没有专门的加密性能基准，不能直接报提升倍数。

代码：[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)、[connection.cc](../rpc_src/network/connection.cc)、[aes_encrypt_test.cc](../rpc_src/test/aes_encrypt_test.cc)。

### 4.3 如何处理加密数据损坏或解密失败？

**面试回答：**

接收时先校验密文格式、版本和最小长度，再执行 GCM 解密并验证认证 tag。只有认证成功，输出才可以交给解压和业务解析；失败时清空明文输出，不能因为解密过程中已经得到部分字节就继续使用。

RPC 收到认证失败或模式不匹配的帧会拒绝通信并关闭连接，客户端返回解码或认证失败，不会降级为明文。日志只记录错误类型和必要的请求上下文，不输出密钥或完整载荷。

**追问：能区分是密钥错误还是数据被篡改吗？**

认证失败可能来自错误密钥、密文损坏或 AAD 不匹配，不能仅凭 tag 校验失败准确断言原因。对外返回有限错误信息，内部结合配置与连接日志定位；无论原因是什么，未经认证的数据都不能进入业务处理。

代码：[aes_encrypt.cc](../rpc_src/encrypt/aes_encrypt.cc)、[message_cycle.cc](../rpc_src/network/message_cycle.cc)。

## 5.序列化与反序列化

### 5.1 为何选择 Protobuf、JSON？如何实现跨语言兼容？

**面试回答：**

我提供 JSON 和 Protobuf 两种适配，是为了覆盖不同使用场景。JSON 可读性好，适合调试和示例；Protobuf 通过 schema 约束类型，并生成多语言消息类，适合约定清晰的接口。项目对普通 C++ 类型使用 nlohmann-json，对 Protobuf 生成类型使用其二进制接口，类型与指定格式不匹配时拒绝调用。

跨语言需要同时约定业务载荷和外层 RPC 帧。各语言可以从同一份 proto 生成消息类型，但还必须实现项目的帧头、字节序和请求响应结构。当前 Echo 使用 JSON，外层帧是自定义二进制协议，因此不能说生成 Protobuf 类就已经完成跨语言 RPC。

**追问：接收方怎么知道序列化格式？**

当前由接口两端约定，协议没有携带序列化类型，也没有自动协商。仓库的 `message.proto` 用于生成类型和序列化验证，没有替换实际外层帧。如果扩展多种业务编码，我会在协议版本中明确编码类型，并让分发层校验方法支持的格式。

代码：[serializer_manager.h](../rpc_src/serializer/serializer_manager.h)、[rpc_service.h](../rpc_src/core/rpc_service.h)、[message.proto](../protos/message.proto)。

### 5.2 如何处理字段增删导致的版本兼容问题？自定义序列化如何优化性能？

**面试回答：**

如果业务消息使用 Protobuf，我会保持已有字段编号不变，新字段使用新编号；删除字段后保留其编号和名称，避免复用，也不随意改变字段类型。旧端可以跳过新增的未知字段，新端需要为缺失字段定义合理语义，再用新旧版本交叉读写测试验证兼容。

JSON 则需要业务显式定义缺失字段的默认值、未知字段处理和类型约束。项目的适配器先解析到临时对象，成功后再更新结果；这能减少解析失败造成的部分更新，但不代表自动完成了业务版本兼容。

**追问：自定义协议怎么优化？**

当前外层协议会预先计算长度、检查上限并预留输出空间，减少重复扩容。下一步我会先分析分配和复制热点，再评估复用缓冲区、移动数据或减少中间对象。异步发送必须保留缓冲区所有权，不能为了减少复制而引用已经释放的数据；这些优化要用编解码基准和端到端测试验证。

代码：[serializer_manager.h](../rpc_src/serializer/serializer_manager.h)、[rpc_protocol.cc](../rpc_src/protocol/rpc_protocol.cc)。兼容规则参考：[Protobuf 字段更新](https://protobuf.dev/programming-guides/proto3/#updating)。

## 6.Zookeeper节点注册

### 6.1 为何选择 Zookeeper 而非 ETCD？临时节点和持久节点的区别？

**面试回答：**

项目使用 ZooKeeper，主要是它的会话、临时节点和 watch 能自然表达服务实例注册与失效通知，而且可以通过 C 客户端接入现有代码。etcd 也能通过租约和 watch 实现类似能力，我没有做过两者的性能与运维对比，因此不会说 ZooKeeper 一定更优，选型还要考虑团队经验和部署环境。

持久节点不会因为创建会话结束而删除，适合服务目录；临时节点属于创建它的会话，随会话结束删除，适合实例注册。项目自动创建 `/cookrpc` 和服务目录作为持久节点，把具体实例地址注册为临时节点。

```text
/cookrpc                                  持久根目录
/cookrpc/cookrpc_service                  持久服务目录
/cookrpc/cookrpc_service/127.0.0.1:8989   临时实例节点
```

**追问：临时节点消失是否等于业务故障？**

它反映的是注册会话是否存活。短暂断线时，会话未过期，临时节点不一定删除；业务卡死但 ZooKeeper 会话还活着，节点也可能继续存在。所以临时节点不能代替业务健康检查。换成 etcd 时，也要重新定义租约续期、失效和 watch 恢复语义。

代码：[service_registry.cc](../rpc_src/registry/service_registry.cc)。机制参考：[ZooKeeper 会话与节点](https://zookeeper.apache.org/doc/current/zookeeperProgrammers.html)、[etcd 租约与 watch](https://etcd.io/docs/v3.6/learning/api/)。

### 6.2 如何实现服务注册与发现？会话超时后如何恢复？

**面试回答：**

服务端先创建持久服务目录，再创建保存实例地址的临时节点。客户端在建连或重连选址时，读取对应目录和实例数据，得到候选列表后负载均衡选址。注册端和发现端使用各自的 ZooKeeper 会话，发现过程目前没有持续实例缓存。

短暂断线由 ZooKeeper 客户端库尝试重连；会话过期后旧会话不能继续使用，需要建立新会话。项目注册端通过后台恢复线程重建会话并重放已确认的注册，发现端则在后续查询时重建。watcher 只更新状态和唤醒线程，不在回调中执行同步重连或注册。

**追问：长连接怎么建立？**

我调用 `zookeeper_init()` 并保存句柄，通过 watcher 和条件变量等待连接成功。非空句柄不代表连接已完成。心跳和临时断线重连由客户端库维护，业务查询复用会话，不每次初始化。代码请求的会话超时为 30 秒，实际值由服务端协商，应用等待连接另有期限。

**追问：实例节点已经存在，直接认为成功吗？**

不能。我会通过 `ephemeralOwner` 判断节点属于哪个会话，并检查地址数据。属于当前会话且数据相同才视为重复注册成功；其他会话持有时，设置 watch，在总期限内等待删除后重试；持久节点占用实例路径或数据冲突则失败。

**追问：注册超时，但服务端其实创建成功了怎么办？**

超时只表示结果未知。当前会退役这个不确定的会话，在锁外关闭后恢复已确认注册，让可能迟到创建的临时节点随旧会话清理。注册总期限覆盖排队、创建、查询和 watch 等待；迟到回调只发布结果，不继续提交业务注册，避免超时后悄悄改变状态。

会话对象同时拥有句柄和 watcher 上下文，查询持有共享快照，避免上下文提前释放。关闭时不持有回调需要的锁，防止 `zookeeper_close()` 等待回调造成死锁。配置切换也是新连接成功后才提交，失败保留旧配置。

代码：[zk_conn_handler.cc](../rpc_src/conn_balancer/zk_conn_handler.cc)、[service_registry.cc](../rpc_src/registry/service_registry.cc)。

## 7.RPC协议定义

### 7.1 如何设计协议头（Magic Number/Version/MsgID/Length）？如何解决粘包拆包？

**面试回答：**

项目使用 12 字节固定头部：4 字节魔数用于识别协议，4 字节 body 长度用于确定帧边界，4 字节请求序列号用于匹配响应。整数使用网络字节序，body 上限是 1 MiB。当前没有独立 Version 字段，传输格式通过不同魔数识别，不能把题目里的所有字段都说成已实现。

TCP 是字节流，一次读取可能只有半帧，也可能包含多帧。我先把数据放进接收缓冲，等头部完整后检查长度，再等待完整 body；解析一帧后继续处理剩余数据。长度超限或结构非法会拒绝，不能按照一次 `recv()` 就是一条消息来处理。

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 字节 | Magic，原始格式为 CRPC |
| 4 | 4 字节 | Body 长度，不包含固定头部 |
| 8 | 4 字节 | 请求序列号 |

**追问：body 内部如何区分字段？**

请求依次保存服务名、方法名和载荷，每个字段前带 u32 长度；响应保存错误码、带长度的错误文本和结果。按长度读取允许字符串包含零字节，解析时仍要逐段检查剩余空间。

**追问：读取到数据，同时又收到 EOF 怎么办？**

先处理已经收到的数据。若其中有完整响应，客户端可以正常完成调用；EOF 时仍缺少帧内容，才判定响应不完整。可读和挂断事件同时出现时也先读取，避免丢掉对端关闭前发送的最后一段数据。

代码：[rpc_protocol.h](../rpc_src/protocol/rpc_protocol.h)、[rpc_protocol.cc](../rpc_src/protocol/rpc_protocol.cc)、[connection.cc](../rpc_src/network/connection.cc)。

### 7.2 协议扩展性如何保证（如预留字段）？如何校验数据完整性（CRC校验）？

**面试回答：**

当前保留了原始 CRPC 格式；启用压缩或加密时使用 CRP1 魔数，仍然是 12 字节头部，body 开头增加一个变换标志字节。标志表示是否开启压缩模式、当前帧是否压缩以及是否加密，接收方拒绝未知标志和配置不匹配，避免把不兼容数据继续解析。

完整性方面，未加密帧目前只有长度和结构校验，没有实现 CRC；加密帧使用 GCM tag 认证 body、头部、标志和方向。CRC 用于检测意外损坏，不能抵抗攻击者修改数据；如果需要防篡改，应使用认证机制。

**追问：后续怎么增加字段并兼容旧端？**

我会定义明确的新版本、头部长度和可选扩展区，并规定未知版本、未知必选能力的拒绝规则，而不是直接改变已有字段含义。这些是扩展方案，当前没有通用的预留字段或能力协商机制，序列化类型也仍由接口约定。

**追问：业务结果过大怎么办？**

逻辑 body 和线上 body 都有 1 MiB 上限。请求超限在发送前失败，响应超限会尝试转换为保留原序列号的短错误响应。加密的 nonce、tag 和 Base64 膨胀也要计入线上长度，不能只检查原始业务结果大小。

代码：[transport_codec.cc](../rpc_src/protocol/transport_codec.cc)、[rpc_protocol.cc](../rpc_src/protocol/rpc_protocol.cc)。

## 8.网络管理模块

### 8.1 使用 Reactor 还是 Proactor 模式？如何实现高并发（epoll+线程池）？

**面试回答：**

项目采用 Reactor。Linux 下使用 epoll 监听非阻塞 socket 的就绪事件，由事件线程接入连接、读取数据并拆出完整帧，再投递给工作线程解码和执行业务。业务完成后把响应放入发送队列，由事件线程实际写入 socket，而不是让工作线程等待慢客户端。

Reactor 通知的是“可以尝试读写”，读写仍由应用执行；Proactor 处理的是异步 I/O 完成事件。这里使用非阻塞 socket 和 epoll，属于前者，不能因为业务异步执行就称为 Proactor。

**追问：短写和慢客户端怎么处理？**

短写时保留发送偏移，遇到 EAGAIN 就订阅 EPOLLOUT，队列清空后取消写事件，避免空转。每连接的队列限制为最多 64 帧且总字节数不超过 4 个最大帧，超限拒绝并请求关闭连接；每轮发送最多 64 KiB，避免一个连接长期占用事件线程。

**追问：怎样避免连接洪峰影响已有请求？**

每轮最多接入 64 个连接，并限制活动连接总数。遇到 fd 或 socket 资源不足时，暂停监听读事件，按 100 毫秒到 1 秒退避恢复，已有连接继续处理。事件注销和 fd 关闭统一由事件线程完成，排队操作携带连接身份，避免 fd 复用后误操作新连接。

当前只有一个事件循环，业务线程池主要隔离耗时工作，不能据此承诺无限并发。单客户端连接上的调用也仍然串行；如果剖析发现事件线程是瓶颈，我会再评估多 Reactor，而不是直接增加业务线程。

代码：[message_cycle.cc](../rpc_src/network/message_cycle.cc)、[connection.cc](../rpc_src/network/connection.cc)。慢读与 fd 复用回归见 [network_test.cc](../rpc_src/test/network_test.cc)。

## 9.综合架构设计

### 9.1 整个 RPC 框架有哪些核心模块？它们之间是怎样协同的？

**面试回答：**

我会沿一次调用介绍核心模块，而不单独罗列类名。服务端启动时通过注册模块发布实例，之后客户端按下面的链路发起调用：

1. 客户端通过 ZooKeeper 发现实例，经过熔断过滤和负载均衡选址，建立或复用 TCP 连接。
2. 序列化模块把参数变成载荷，协议模块封装服务名、方法名和序列号，传输模块按配置压缩、加密后发送。
3. 服务端事件线程读取并拆帧，通过限流检查后交给线程池；工作线程解码，再由服务管理器找到业务处理器执行。
4. 结果编码成响应，进入有容量限制的发送队列，事件线程负责实际写出。
5. 客户端解码、检查序列号和错误码，将结果反序列化，并更新实例的熔断状态。

日志和配置为各模块提供基础能力。当前示例调用的是 JSON 编码的 `RpcService.Echo`；发现目录 `cookrpc_service` 用于找地址，业务服务名 `RpcService` 用于请求分发，二者职责不同。

**追问：同步和异步接口的区别是什么？**

客户端 `AsyncCall` 通过后台任务调用共享会话的同步接口，再用 future 返回结果；同一个会话上的调用仍然串行，没有实现连接内多请求复用。服务端则通过事件线程和业务线程池并行处理多个请求，不能把这两种异步能力混为一谈。

代码：[rpc_client.h](../rpc_src/core/rpc_client.h)、[message_cycle.cc](../rpc_src/network/message_cycle.cc)、[service_manager.h](../rpc_src/service/service_manager.h)。

### 9.2 如何保证模块间低耦合？

**面试回答：**

我主要按职责划分边界：网络层负责连接和字节流，协议层负责帧与字段，序列化层负责业务对象转换，注册发现层负责实例地址，服务层负责业务处理。业务通过统一的 `Service` 接口接入，`ServiceManager` 根据服务名查找处理器，网络层不需要理解 Echo 的业务字段。

传输变换封装在 `TransportCodec`，业务层使用还原后的请求，不需要关心是否压缩或加密。这样可以分别测试协议、序列化和业务。但当前负载均衡、日志和线程池仍有全局共享状态，不能说已经实现完整依赖注入；如果扩展，我会优先把这些依赖通过构造参数传入。

**追问：异步任务如何避免悬空引用？**

客户端后台任务持有共享会话，服务任务持有处理器快照，并通过拥有结果数据的 `future<AsyncResult>` 返回，避免捕获外部输出变量引用。线程池同样先在锁内取得共享指针，再在锁外执行操作；共享所有权保护生命周期，状态访问仍需要各自同步。

**追问：线程池退出如何保证资源安全？**

我把请求关闭与等待退出拆开。关闭后拒绝新任务、解除暂停并排空已接收任务；等待超时只返回未完成，不强制终止业务线程，也不立即释放任务依赖的状态。线程句柄在受保护的容器中移出，再锁外 join，并协调并发关闭，避免重复 join 或工作线程等待自己退出。

代码：[service.h](../rpc_src/service/service.h)、[service_manager.h](../rpc_src/service/service_manager.h)、[thread_pool.h](../rpc_src/thread_pool/thread_pool.h)、[thread_pool_singleton.cc](../rpc_src/thread_pool/thread_pool_singleton.cc)。

### 9.3 如何测试 RPC 框架性能（压测工具/指标）？如何定位内存泄漏？

**面试回答：**

项目有独立压测客户端和脚本，使用多个客户端连接并发调用 JSON Echo，可以按请求数量或持续时间执行。我会固定硬件、构建模式、消息大小、日志级别和限流配置，再逐步增加并发，观察吞吐量、成功率、P50/P95/P99 延迟，以及服务端 CPU、内存和队列积压，找出容量拐点。

定位内存问题时，我会单独构建 ASan/UBSan，结合 LeakSanitizer 查看分配栈和未释放对象；数据竞争使用另一套 TSan 构建。还会反复连接、断开、重连和关闭服务，观察堆内存、线程数及 fd 是否持续增长。RSS 增长只是线索，需要区分真实泄漏、缓存和分配器保留内存。

**追问：如何运行和解释压测？**

```bash
# 启动 ZooKeeper 和 RPC 服务端后，从仓库根目录执行
./stress_test.sh -c 50 -r 200
./stress_test.sh -c 20 -t 120 --payload-size 4096
```

客户端准备完成后开始计时，每个连接串行调用，多个连接形成并发。到期后停止提交并等待在途调用完成。吞吐量按完成调用计算，成功率单独报告；延迟包含成功和失败调用，时长模式的百分位由固定大小直方图估算。这个负载模型不能代表所有线上流量，也不能忽略错误率只报 QPS。

**追问：测试覆盖到真实网络和注册中心了吗？**

常规测试包含真实本地 TCP，以及通过替换 ZooKeeper API 控制交错的注册发现测试；可选集成测试会启动真实 ZooKeeper，覆盖会话过期、重启恢复和慢读背压。并发测试尽量用 promise 或屏障控制时序，减少靠 sleep 碰运气。性能与 Sanitizer 测试使用不同构建，命令见 [README 测试说明](../README.md#测试)。

代码：[stress_test_client.cc](../rpc_src/tools/stress_test_client.cc)、[stress_test.sh](../stress_test.sh)、[live_test.py](../rpc_src/test/live_test.py)。

### 9.4 如何实现流量控制（限流/熔断）？如何监控系统健康状态？

**面试回答：**

服务端使用进程级令牌桶，通过单调时钟按速率补充令牌，桶容量允许有限突发。完整帧入线程池前检查配额，超限返回错误码 3005，不占用后续解压和业务执行资源。再结合任务队列、响应队列和连接数上限控制积压，限流与背压分别限制进入速率和待处理资源。

客户端按实例地址维护熔断状态。连续远端连接、收发或协议失败达到阈值后打开熔断；冷却后允许单次探测，成功恢复，失败重新冷却。默认阈值为 5 次、冷却 5 秒；有效业务错误和限流响应不计通信故障，本地参数或套接字资源错误也不应该误伤远端实例。

**追问：怎样监控，是否已经接入监控平台？**

当前有线程池统计和日志，可查看队列、任务成功失败、耗时及线程情况，但没有独立监控导出接口。扩展时我会导出请求速率、错误率、延迟分布、活动连接、队列利用率、限流次数、熔断状态以及 ZooKeeper 会话状态，并为持续异常设置告警；业务健康还需要轻量探测。

**追问：发现部分失败，会不会清掉原来的熔断状态？**

只有目录和全部实例数据都读取成功，才按这个快照清理缺失实例的历史。部分读取失败不能说明实例已经消失，所以保留原状态。当前熔断是客户端会话内的，限流是服务端进程总配额，尚未实现跨进程统一配额或按方法限流。

代码：[request_controls.cc](../rpc_src/core/request_controls.cc)、[rpc_client.cc](../rpc_src/core/rpc_client.cc)、[thread_pool.h](../rpc_src/thread_pool/thread_pool.h)。

### 9.5 有哪些手段保证高可用？

**面试回答：**

当前实现提供多实例发现、随机或轮询分流、有限建连重试和实例熔断，减少单个故障实例的影响；服务端注册会话过期后自动恢复注册，ZooKeeper 配置切换失败时保留旧配置。真实集成测试覆盖了会话过期及 ZooKeeper、TCP 服务重启后的恢复，但恢复过程中仍可能调用失败，不能承诺无损切换。

如果面向生产，我会进一步部署注册中心集群，增加业务健康检查、明确摘除与恢复规则，设计发现缓存及其过期策略，并根据请求幂等性限制重试。当前配置构造的是单个 ZooKeeper 端点；支持集群地址列表还需要扩展配置解析，不能只把部署多个节点说成代码已经支持。

**追问：优雅退出怎么做？**

收到退出信号后，先停止接收新请求，事件循环最多等待 3 秒尝试发送在途响应，再关闭剩余连接；随后请求线程池排空，先按配置等待，再继续等待任务结束，最后清理注册会话。有限等待不是取消承诺，普通 C++ 业务任务不能被安全强制终止，退出时间可能超过等待配置。

当前注册信息在退出流程后段清理，所以退出期间客户端仍可能发现这个实例。如果完善，我会增加摘流步骤并明确传播等待窗口，同时定义外部进程管理器的最终退出期限。

代码：[servers_main.cc](../rpc_src/core/servers_main.cc)、[message_cycle.cc](../rpc_src/network/message_cycle.cc)、[service_registry.cc](../rpc_src/registry/service_registry.cc)。

### 9.6 用到了哪些性能调优方法？

**面试回答：**

当前实现主要从三个方面控制成本：网络侧使用非阻塞 I/O、长连接和批量事件处理；调度侧让工作线程执行业务，响应由事件线程发送，并限制每轮 I/O 和队列容量；数据侧预估协议长度并预留空间，压缩只对达到阈值的消息尝试，且输出更小才采用。

并发方面，负载均衡在取得策略快照后释放全局锁再选址，避免把策略执行放在全局临界区。线程池支持按需扩容和空闲回收，后续提交或扩容时也会回收已退出线程的句柄，控制反复扩缩容的资源积压。

**追问：优化带来了多少提升，下一步怎么做？**

这些是已经落地的机制，但目前没有可直接引用的统一前后对比数据，我不会报固定提升比例。下一步会用性能剖析确定 CPU、锁、分配还是事件线程成为瓶颈，再分别评估异步日志、缓冲区复用或多事件循环。每项只改变一个主要因素，对比吞吐量、P99 和资源占用，防止局部更快但整体退化。

代码：[connection.cc](../rpc_src/network/connection.cc)、[load_balancer.cc](../rpc_src/conn_balancer/load_balancer.cc)、[thread_pool.cc](../rpc_src/thread_pool/thread_pool.cc)。

## 10.其他

### 10.1 protobuf与json相比较，优势在哪里？

**面试回答：**

Protobuf 的优势主要是二进制表达通常更紧凑、schema 明确，并能生成多语言的类型与编解码接口。字段通过编号表示，减少重复字段名和文本转换开销；稳定的编号规则也便于演进接口。JSON 的优势是可读、调试方便，适合开放接口和人工排障。

选择要看消息结构、兼容要求和工具生态，不能说 Protobuf 在任何数据上都更小更快。项目同时提供两种适配器，但 Echo 和压测目前用 JSON，没有完成同一 schema 的公平性能对比。

**追问：为什么提供 Protobuf，却还用 JSON 做示例？**

JSON 让示例请求和返回值更直观，便于先验证发现、传输和分发链路。要使用 Protobuf，需要把业务方法的载荷类型与解析方式一起约定好；只把客户端序列化选项改成 Protobuf，不能让现有 JSON Echo 自动兼容。

代码：[serializer_manager.h](../rpc_src/serializer/serializer_manager.h)、[rpc_service.h](../rpc_src/core/rpc_service.h)。

### 10.2 protobuf怎么编译成对应的语言代码？c++，java，python

**面试回答：**

先编写 proto 文件定义消息，再用 `protoc` 通过不同输出参数生成各语言代码。`-I` 指定 proto 的搜索路径，`--cpp_out`、`--java_out` 和 `--python_out` 分别指定输出目录。生成代码之后，还需要对应语言的 Protobuf 运行时；C++ 文件还要参与编译和链接。

```bash
# 在仓库根目录执行；先创建输出目录
mkdir -p generated/cpp generated/java generated/python

protoc -I protos --cpp_out=generated/cpp protos/message.proto
protoc -I protos --java_out=generated/java protos/message.proto
protoc -I protos --python_out=generated/python protos/message.proto
```

**追问：项目构建时怎么处理？**

项目正常构建由 CMake 调用依赖中的 protoc，把 C++ 文件生成到构建目录的 `generated/` 并加入公共库，不需要手动生成进源码目录。上面的命令用于解释多语言生成；它们只生成消息类型，不能生成本项目自定义 TCP 协议的完整客户端和服务端。

代码：[CMakeLists.txt](../CMakeLists.txt)、[message.proto](../protos/message.proto)。命令参考：[Protobuf 代码生成](https://protobuf.dev/programming-guides/proto3/#generating)。

### 10.3 protobuf可以自定义json tag，这个有什么用？

**面试回答：**

如果这里的 json tag 指 Protobuf 的 `json_name`，它用来控制消息转换成 ProtoJSON 时的字段名，方便与已有 JSON 接口命名对齐。例如内部字段叫 `service_name`，对外接口要求叫 `service`，可以显式指定。

```proto
string service_name = 2 [json_name = "service"];
```

这里特意使用与默认驼峰名不同的 `service`，更容易看出自定义效果。`serviceName` 本来就是 `service_name` 的默认 ProtoJSON 名称，并不一定需要显式配置。

**追问：会改变二进制协议吗？**

不会。二进制格式仍按字段编号 2 编码；`json_name` 影响的是 ProtoJSON 映射。它也不会自动改变项目中 nlohmann-json 的字段映射。当前 `message.proto` 没有设置该选项；若改变已经对外使用的 JSON 键名，需要单独评估 JSON 客户端兼容性。

参考：[ProtoJSON 字段表示](https://protobuf.dev/programming-guides/json/#representation)。

### 10.4 同样一个对象，用json和protobuf存，protobuf是怎么存的，为什么可以做到体积比json小？

**面试回答：**

JSON 会把字段名和值一起写成文本，Protobuf 则记录字段 tag 和字段值，由接收端的 schema 解释含义。tag 由字段编号左移 3 位，再加上 wire type 得到。整数可以使用 varint，小整数占用较少字节；字符串保存字节长度和内容，不重复写完整字段名。

例如下面的消息和值：

```proto
message User {
  int32 id = 1;
  string name = 2;
}
```

```text
JSON：{"id":150,"name":"Li"}
Protobuf 十六进制：08 96 01 12 02 4C 69
```

`08` 表示字段 1、varint 类型，`96 01` 编码 150；`12` 表示字段 2、长度限定类型，`02` 是长度，最后两个字节是 Li。这个例子二进制载荷只有 7 字节，没有包含项目外层 RPC 帧头和其他元数据。

**追问：Protobuf 一定更小吗？**

不一定，还要看字段编号、数值范围和消息内容。proto3 隐式存在的普通标量字段在默认值时通常不编码；显式存在字段规则不同。负数 int32 的 varint 可能占较多字节，可以按语义选择 sint32；不能通过随意换类型破坏已有接口兼容性。

参考：[Protobuf 二进制编码](https://protobuf.dev/programming-guides/encoding/)。

### 10.5 protobuf为什么序列化和反序列化比较快？

**面试回答：**

主要原因是生成代码事先知道字段类型，编码时可以直接按二进制规则写值，解码时根据 tag 和长度分发，减少字段名匹配、字符串转义和数字与文本之间的转换。JSON 通常还要解析这些文本结构，所以 Protobuf 在很多结构化消息上更有优势。

但二进制不等于零成本，Protobuf 仍有内存分配、字符串复制和变长整数处理，具体结果也依赖消息结构、运行时和 JSON 库实现。对于很小的 RPC 消息，网络和调度开销可能比编解码更大，单独的序列化优势不一定能转成同等的端到端收益。

**追问：怎么证明在这个项目里更快？**

我会对同一份业务数据分别实现 JSON 和 Protobuf 编解码，在相同编译选项下测单次耗时、吞吐量、体积和分配情况，再接入相同 RPC 路径比较 P99 与 CPU。当前压测只覆盖 JSON Echo，不能把库的通用特性或官方基准直接当成本项目已经验证的性能结论。

代码：[json_serializer.h](../rpc_src/serializer/json_serializer.h)、[protobuf_serializer.h](../rpc_src/serializer/protobuf_serializer.h)。编码原理参考：[Protobuf encoding](https://protobuf.dev/programming-guides/encoding/)。
